# BlazorCodeFirst Architecture

**Internal architecture: the compilation algorithm, sequence assignment, memory layout**

Target environment: .NET 10 (baseline), .NET 11 (conditional features)

> For background, goals, and usage, see `DESIGN.md`.

---

## 0. Notation and assumptions

Symbols are used only where this design's core needs to be stated precisely: the sequence-number stability conditions (§1.2). There, basic set and mapping notation is used (`f : A → B` for a mapping, `|X|` for cardinality). Everywhere else is ordinary prose.

Language and runtime features this specification depends on:

| Feature                                                | Requirement                            | Use                                          |
| ------------------------------------------------------- | --------------------------------------- | --------------------------------------------- |
| Source Generator member generation into a partial class | Every supported version (a mature, standard feature) | Generating `RenderView` (§2)          |
| IL trimming / Native AOT                                 | .NET 10                                 | Removing the inert API and unused code (§5)   |
| `closed` hierarchies                                     | C# 15 / .NET 11 (conditional)           | `ViewNode`'s closed-world definition (§6)     |
| Runtime Async                                            | .NET 11 (conditional)                   | Lightening the event pipeline (§4.3)          |

That the core mechanism does not depend on any particular bleeding-edge language feature is a deliberate property of this design. Alternative architectures considered and rejected (an Interceptor-based approach, a runtime ref-struct-tree approach) and why are recorded in Appendix B.

## 1. Abstract mathematical model and formal definitions

### 1.1 State and projection

Let `S` be a component's state space, and `s_t` (`s_t ∈ S`) the state at time `t`. Let `R` be the set of Blazor's internal rendering trees (frame sequences), and `r_t` (`r_t ∈ R`) the frame sequence generated at time `t`. `R` and `r_t` are used in the diff-detection stability condition (§1.2).

At build time, the Source Generator compiles a design-time UI expression into "a function that takes a state and returns a frame sequence" (typed as `S → R`). Only this generated function runs at run time, and `r_t` is the result of applying it to state `s_t`. The UI expression itself (the design-time syntactic entity) is never evaluated at run time. Contrasted with Razor: the Razor compiler takes this same input as markup, where BlazorCodeFirst takes it as a C# expression.

It is a convention that the generated function is pure — it depends only on state and carries no side effects (single-direction data flow, §4.1). A state mutation inside a design-time expression (`BodyComponentBase.Body` or `ChromeLayoutBase.Chrome`) is covered by diagnostic BCF3001. BCF3001's initial detection scope is limited to a statically identifiable direct write to a component instance member (field assignment, property assignment, compound assignment, the increment/decrement operators). A mutation inside a deferred handler argument, such as a `Button`'s onClick lambda, is excluded because it runs after rendering; the excluded positions are defined by Appendix A's BCF3001 row. Complete detection of a side effect reached through an arbitrary method call (e.g. an async chain) is not guaranteed in the initial slice.

### 1.2 Rendering-tree equivalence and diff detection

Each frame `n ∈ r_t` in `R` carries a sequence number `seq(n) ∈ ℕ`. Let Blazor's diff operator be

```
Δ : R × R → Patch
```

and `Δ(r_t, r_{t+1})` is applied to the DOM. Blazor's diff algorithm walks both trees simultaneously from the start, and judges frame identity (retain/insert/delete) purely by comparing sequence numbers for equality and ordering.

**Theorem 1 (sequence stability condition)**
For `Δ` to run at minimum cost O(|r_t| + |r_{t+1}|) and preserve the state of semantically identical nodes, the following must hold for every semantically identical node pair `(n, n′)` (`n ∈ r_t`, `n′ ∈ r_{t+1}`):

```
seq(n) = seq(n′)                                   … (1)
```

**Corollary 1**: A sufficient condition to satisfy condition (1) is that `seq` is a function of the syntactic position in source code rather than the run-time generation order. Letting `π(n)` be the syntactic position of the expression node that generated the frame, there exists an injection `σ` such that:

```
seq(n) = σ(π(n)),   σ : Π → ℕ is an injection      … (2)
```

In this approach, `σ` is constructed by the Source Generator at build time and embedded into the generated code as literal constants, so condition (2) is satisfied structurally. In contrast, a runtime-increment approach (`seq(n) = generation order`) violates condition (1) the moment conditional rendering or element insertion breaks the correspondence between `π` and generation order, degrading to an O(n) walk.

What follows a violation of condition (1) splits on whether a key is present (measured figures: `DESIGN.md` §7.2). Without a key, the frames from the point that should have matched onward are misjudged as "delete plus fresh insert," and the internal state of the reconstructed component (in-progress text input, for example) is lost. That range still depends on a structural condition, though: when the offset is a multiple of a node's frame width, a later node matches at a position shifted by one, so the loss is confined to the tail and the rest becomes a text rewrite. With a key, on the other hand, key matching within the sibling group holds, so state survives even when the sequence shifts. State loss, in other words, only occurs where a condition-(1) violation and the absence of a key coincide — it does not follow from a condition-(1) violation alone.

State preservation depends on the sequence number being fixed to syntactic position specifically where a region (`OpenRegion`, §5.3) is involved. If a region's own sequence shifts, the whole region is discarded, and because key matching only operates within a sibling group, it cannot rescue the state. In this design, where `If` / `ForEach` each emit a region, condition (2) is essential in exactly this sense.

## 2. The compilation algorithm

### 2.1 The overall pipeline

```
[User code]                          [Source Generator]
partial class C :                    ① partial verification, Body discovery
BodyComponentBase                 ② SSC classification (§2.3)
  View Body => …        ──AST──▶    ③ DFS-order sequence assignment (§2.2)
  [ViewPart] View F() => …         ④ Generating RenderView(RenderTreeBuilder)
                                        — embedding static seq constants
                                        — transplanting dynamic expressions/lambdas as syntax
                                        — inline-expanding [ViewPart]
```

The output is a `RenderView` override in the same partial class, called from the base class's (`BodyComponentBase`, or a layout's `ChromeLayoutBase`) `BuildRenderTree`. Both the design-time expression (`BodyComponentBase.Body` or `ChromeLayoutBase.Chrome`) and the design-time API are unreachable at run time, and the IL trimmer removes them in an AOT build. The design-time API here means every member of `Html` and `Decorations`, and every member of the design-time inert types `View` / `ComponentView<T>` / `ElementView` (Appendix A, BCF3014). The design is verifiable by checking, via `System.Reflection.Metadata`, that no MethodDef remains; the trim tests carry out that verification.

A design-time expression's getter **must reach exactly one `return`**. The three spellings `=> expr` / `get => expr` / `get { return expr; }` are identical, and each generates the same `RenderView`. Local declaration statements and expression statements may precede that `return`. This is the same shape `ForEach`'s `content` accepts (§2.3 Transplantable), and the written statements are transplanted ahead of frame emission. One implementation reads this shape: `RenderExpressionAnalyzer.TryReadTransplantableBlock` answers for both the getter and `content`. Being able to place statements does not permit side effects — a state mutation is still BCF3001. Four shapes remain as BCF1004: a second `return`; a native control construct; a local with a generator-reserved name (the `__bcf_` prefix and `__builder`); and an auto-property that declares no getter body to translate. A re-abstraction (`abstract override`), and a partial property with no implementing part, are excluded — CS9248 names the cause of the latter. A design-time expression is inert syntax never evaluated at run time, and this constraint is simply the premise of "translating syntax statically."

Hand-writing an override of `RenderView` instead of a design-time expression is legal, and is the escape hatch for a body the SSC subset cannot express. In this case the generator produces nothing — generating one would duplicate the member name into CS0111, leaving the author no option but to delete their own code. The design-time expression goes unused, and BCF1004 is not reported either.

The declaration shape recognized as a BlazorCodeFirst component is a top-level `partial class`. Generics (`partial class Foo<T>`) are supported, and the generated part repeats the same type parameter names (it does not repeat the constraint clause — a constraint belongs to the type parameter, so having it on one declaration is enough). A nested type is rejected by BCF1005. A `record` can only inherit `object` or another `record` (CS8864), so it cannot be a BlazorCodeFirst component.

### 2.2 Sequence assignment

`Body`'s expression tree `e` is walked depth-first (preorder), reserving a disjoint sequence range for each UI node. `counter` is not an absolute offset in the source code, but an integer assigned by the syntax tree's logical preorder walk order (a preorder ordinal). This guarantees that a change to a comment or whitespace never affects sequence-number stability.

```
procedure Compile(e: ExpressionTree, model: SemanticModel) → RenderView:
    counter ← 0
    code ← ∅
    for each node v in DFS-Preorder(e):
        match Classify(v, model):
            case Factory(kind) | Decorator(kind):
                w ← EmittedWidth(v)                 // the frame count this node emitted (emission is authoritative, §2.7(D))
                code += EmitFrames(kind, v.Args, seqBase: counter)
                counter ← counter + w
            case Combinator(If | ForEach):
                code += ExpandCombinator(v, ref counter)   // §2.4
            case ViewPartCall(m):
                code += Compile(Body(m), model)            // inline expansion (recursive)
            case Transplantable(stmt):                     // a native if/foreach, etc.
                code += WrapInRegion(Transplant(stmt), seq: counter); counter += 1
            case Opaque(expr):                             // a non-[ViewPart] View-returning call, etc.
                code += WrapInRegion(EmitFragmentOf(expr), seq: counter); counter += 1
                report BCF2001(v)
    return code
```

The pseudocode above is written as a per-node loop, but the unit of folding is **a run of consecutive siblings** (§2.7(D)), and the whole run is emitted as one `AddMarkupContent`. So it is the emission itself, not the node kind, that determines the width (§2.7(B)). No implementation computes the width independently, and none should be added.

`FrameWidth` counts only the `RenderTreeBuilder` calls that consume a sequence argument, and excludes calls with no sequence argument such as `CloseElement`/`CloseRegion`. It is determined by the node kind and by whether that node can be folded. For example: a `Span` with no children = 1 [`OpenElement`]; a `Span` with one **dynamic** string child (`Span[$"...{x}"]`) = 2 [`OpenElement` + `AddContent`]; a `Button` with one onclick attribute = 3 [`OpenElement` + `AddAttribute` + `AddContent`]. An event blocks folding, so this is the width even when the `Button`'s child is constant. A `Span` with one **constant** string child (`Span["..."]`), by contrast, is itself foldable, so its width is 1 (a single `AddMarkupContent`).

Within a decoration chain, `class` is statically composed into the parent element's `class` attribute, so adding `.Class` never increases the frame count (`.Class("a").Class("b")` folds into a single `AddAttribute`). The folded value is assembled after first clearing away the terms readable at compile time. A constant `null` term drops; adjacent constant strings fold into one literal; and only when two or more terms remain does it call the `private static` join the generated class keeps for itself. Because this join skips `null` terms at run time, the separating space disappears along with the term (#236). `AddAttribute` is still emitted even when every term drops, so the frame width is determined purely by the number of decorations and never moves with the value (#234).

An attribute or event decoration other than `class` (`.Href` / `.Attr` / `.OnClick` / `.On`, and so on) adds one frame per decoration (details in §2.7(A)). The exception is `.Bind`, which adds two — an attribute frame and an event frame — per instance; any number can be placed on the same element, and these two frames stack that many times (§2.7(A)). A dynamic argument (an interpolated string, a state reference, an event lambda) is never evaluated — it is transplanted as syntax into `EmitFrames`'s output. Because it is generated inside the same partial class, `private` access via `this` is preserved.

When a value expression is transplanted into generated code, a resolved type name is normalized to its fully-qualified form starting with `global::`. An unresolved type name becomes BCF3015, since a spelling that depends on the original file's `using`s or namespace cannot be transplanted safely as-is. A type reference the author already wrote from `global::`, however, is left to ordinary C# name resolution, since it does not depend on lexical context. A generic type's outer type and each type argument are judged independently. Only a deconstruction declaration's `var` is left exactly as written, because the language allows no type at all before a parenthesized designation — there is simply no shape there in which a normalized name could be written (#342).

`Html.Fragment` (wrapperless grouping) opens no frame of its own, so its `FrameWidth` is the sum of its children's `FrameWidth` (the same shape as a `[ViewPart]` expansion node with no local variables). When every child is foldable, though, the whole fragment becomes one run and its width is 1 (§2.7(D)). `Html.Raw` (trusted raw HTML injection) is a single frame that only emits one `AddMarkupContent`, `FrameWidth` = 1 (the same shape as `AddContent` for a childless string content node). Neither opens an element/component frame, so neither can serve as the root of a `ForEach`'s `content` (BCF3003), nor can either be decorated (BCF3008, details in §2.7(A) and Appendix A).

That decoration is not allowed is also expressed in the type system: a decoration is an extension of `ElementView`, and `Fragment` / `Raw` are `View`, so it is CS1929. BCF3008 is still reported because this CS1929 never reaches the author. A component whose design-time expression cannot be translated has no `RenderView` generated, and the class always carries the declaration-stage error CS0534, so `csc` never proceeds to binding the method body. A real-MSBuild measurement taken before `RejectedDecorationScanner` existed found that fixture `Bcf3008Host` reported only CS0534 and BCF1003 — no CS1929 appeared. Now that BCF3008 is reported, the same fixture reports it too. BCF1003 reaches the author in the same build. Only a generator diagnostic can get past this cutoff.

### 2.3 The statically sequenceable subset (SSC)

Condition (2)'s `σ` cannot be constructed for arbitrary C# code, because the call graph is only settled at run time. The scope of the analysis is classified into the following three tiers:

**SSC (fully static)**: subject to static sequence assignment.
- SSC-1: direct writing of an element helper/decoration, and a direct call to `Component<T>()`, `Fragment`, or `Raw`, in a `Body` body or a `[ViewPart]` method body
- SSC-2: the `If(cond, then, otherwise)` combinator (both branches must be inline lambdas)
- SSC-3: the `ForEach(source, key, content)` combinator (`content` an inline lambda, `key` an inline expression lambda or a written `null`), and its sugar, the spread `[.. <source>.Select(<inline expression lambda>)]` inside a child list (which folds into the same node, matching down to not emitting `SetKey`)
- SSC-4: any nesting of SSC-1 through SSC-3, and static inline expansion of a `[ViewPart]` call

**Transplantable (syntax transplant)**: a statement is transplanted whole into generated code and wrapped in a boundary region (§2.5). Four shapes are accepted. The first three are written in the same three positions: a block-bodied lambda written in `ForEach`'s `content`, a design-time expression's (`Body` / `Chrome`) getter, and a `[ViewPart]`'s body. In the first the statements fall inside the loop; in the second, ahead of `RenderView`'s frame emission; in the third, into the expansion site. The fourth shape (#316) — a native `foreach` ending in one `yield return` — reaches only the third of these positions, a `[ViewPart]`'s body: neither of the other two can substitute a loop for their own trailing `return`, since returning inside a loop body exits after the first item and not returning on every path is CS0161, so the only spelling that both compiles and means "produce every item" is a C# iterator — and a getter cannot be one (CS1624) any more than a lambda can (CS1621). The language excludes the other two positions before this analysis is ever reached. The diagnostic splits by position: `content` is BCF3004, the getter is BCF1004, and `[ViewPart]` (all four shapes it accepts, the fourth included) is BCF1002.

The first shape is a block containing local declaration statements and expression statements, ending in exactly one `return <SSC expression>;`. A transplanted statement contains no call that takes a sequence argument, so the sequence width is the same as writing a single expression — this shape carries full static width, the same as SSC.

The second shape (`TryReadTransplantableIf`) is a block ending in a native `if`/`else` instead of a `return`, each of whose arms recursively satisfies one of these three shapes (so an `else if` chain, and a leading local declared inside an arm before its own `return`, are both accepted). Unlike the first shape, this one degrades: because only one arm ever executes, no static width can be reserved for an arm that might not run, so each arm's content is drawn through a freshly synthesized `RenderFragment` rather than assigned its own sequence range (§2.5, and contrast §2.4's disjoint per-branch ranges for `If()`). Notified by diagnostic BCF2002 (Info), reported once per chain at its outermost `if`.

The third shape (`TryReadTransplantableSwitch`) is a block ending in a native `switch` instead of a `return`, the same degradation as the second shape for one more C# branch construct: each section's statements (`AnalyzeSwitchSection`) recursively satisfy one of these three shapes (so a section ending in a nested `if` or a nested `switch`, and a leading local declared inside a section before its own nested construct, are both accepted the same way a nested `if`/`else` is), and each section's content shares the second shape's single sequence number rather than a disjoint range, since only one section ever runs. A section's own labels are not themselves one of the three Transplantable shapes — a label is neither a statement nor a `return`ed expression — but a pattern label (`case Foo f:`) or a `when` clause can reference an enclosing scope's identifier the same way a leading statement or a discriminant can, so each label is normalized through the same hole substitution (`ExpressionTemplateFactory.CreateForSwitchLabel`) rather than transplanted as raw text. `goto case`/`goto default` is not one of the accepted trailing shapes (a `return`, a nested `if`, or a nested `switch`), so it is rejected the same way any other statement `AnalyzeSwitchSection` does not recognize is — it is not a construct this shape's grammar excludes by name. Notified by the same diagnostic BCF2002 (Info) as the second shape, reported once per `switch` at its discriminant.

The fourth shape (`TryReadIteratorForEach`) is a block ending in a native `foreach` whose own body is braced and ends, in its own last statement, in exactly one `yield return <SSC expression>;`. Only local declaration statements and expression statements are permitted both ahead of the outer `foreach` and ahead of that trailing `yield return` inside the loop body. A second `yield return`, a `yield` outside the loop, `yield break`, `break`, `continue`, a nested control-flow construct, a braceless loop body, `await foreach`, and a deconstructing `foreach (var (a, b) in …)` are each excluded structurally by this shape's own grammar, not by a separate scan for each — every statement position this shape does not name a role for is read as a plain leading statement or rejected outright, and nothing outside a `LocalDeclarationStatementSyntax`/`ExpressionStatementSyntax` is one. Unlike the second and third shapes, this one does not degrade: the loop body's tail is a single SSC expression that every iteration reuses through one static range, the same as `ForEach`'s own `content`, so this shape is classified into the very `ForEachNode` the `ForEach` combinator itself builds and reuses its emission (`EmitForEach`, §2.4, §2.7(B)) rather than the freshly synthesized per-arm `RenderFragment` the second and third shapes need — and is therefore never subject to BCF2002. `Key` on that `ForEachNode` is always `null`: a native `foreach` header carries no sibling `key` argument to bind, so a per-item key is instead written as the yielded element's own `.Key(...)` frame decoration, the same as any other element's. When the header declares its iteration variable with an explicit type rather than `var` — legal C# whenever the source's element type converts to it — the emitted `foreach` carries that same explicit type rather than `var`, so a call whose receiver depends on the narrower type still binds in generated code the way it does in the author's own file.

Multiple `return`s are not accepted, since each would need its own sequence space. A native `foreach` was excluded under that same reasoning until #316 added the fourth shape above; the premise did not actually hold for it — a loop's trailing `yield return` needs no sequence space of its own, since it is one static range every iteration reuses, exactly as `ForEach`'s own `content` is. It is accepted, but only at the `[ViewPart]` position, since only a method can be a C# iterator.

A local a `[ViewPart]`'s body binds into an enclosing scope receives a generated name only at that definition (#336, #343). Because the definition's body is duplicated at every call site, a name the author wrote can end up declared twice in one generated scope. There are two binding paths: a local the leading statement declares, and a designation in the return expression (a pattern variable, `out var`, a deconstruction). An expression body that has only the latter also receives this renaming. The inside of a lambda is excluded. Because both an `If` branch and a `ForEach`'s content fall into their own braces in the generated code, the two expansions never meet in one scope. The renaming uses the same mechanism as an iteration variable: both the declarator's identifier and its references are carried by the same hole, and the expansion casts the name. The design-time-expression side keeps the written name as-is, because within a single design-time expression the author's nesting and the generated code's nesting coincide, so the written name is always legal there (sibling blocks become sibling generated scopes, and if a getter's local and a block's local shared a name, the author's own file would already be CS0136).

There are six positions that accept a local from the enclosing scope: two headers of lowered syntax (#361), and four headers of native syntax admitted for the same reason (#569, and #316 for the fourth). An `If`'s condition falls into the generated `if`'s header, enclosing both branches — true of both the lowered `If(...)` call and a native `if`/`else` (§2.3's second Transplantable shape, which lowers to the same header shape, `EmitTransplantedIf`), so a pattern designator the author wrote in a native `if`'s own condition is as legal in either branch as one written in a lowered call's condition argument. `ForEach`, and the source of its sugar `..source.Select(…)`, falls into the generated `foreach`'s header, enclosing the loop body; `key`'s body falls into that loop body's `SetKey`, so it reads the same way. A native `switch`'s discriminant (§2.3's third Transplantable shape) falls into the generated `switch`'s header the same way an `If`'s condition does, enclosing every section. A `case` label's own pattern designator is narrower: C# scopes a label's designator to that one section, not the whole `switch`, so it is registered and released once per section rather than once for the whole construct — and that narrower boundary is not one this rule's own tests can pin, because a reference from a sibling section is already invalid C# in the author's own file (CS0103) before BCF1002 is ever reached. A native `foreach`'s own source expression (ARCHITECTURE.md §5.3's Transplantable syntax, extended to the shape `if`/`switch` cannot cover) falls into the generated `foreach`'s header the same way `ForEach`'s own source argument does, enclosing the loop body — but only the source expression, never the whole statement: the statement's own yielded expression can itself contain several sibling constructs, each normalized against its own root, so a scope wide enough to cover the whole statement would wrongly admit a local declared in one sibling's own header to a reference from a different sibling. The loop's own iteration variable is therefore not admitted through this span-containment mechanism at all — its only declaring span is the whole statement, too wide to push — but is instead exempted by symbol identity (`ViewPartBodyContext.PushIterationVariableExemption`), a narrower, separate mechanism from every other position here. Registration uses the same mechanism as a transplanted block (`ViewPartBodyContext.PushTransplantedScope`), and since both a design-time expression and a `[ViewPart]` read the same check, every position closes together.

Acceptance is limited to these, and simple containment is not enough to judge it — the reason differs by position. A component's slot has its contents wrapped in a single `RenderFragment` lambda, so a local declared in one slot reaches neither a sibling slot nor a sibling parameter. An element's siblings, conversely, do line up into one block, but not in the author's order: the class channel falls ahead of the attribute loop, event and bind decorations fall after it, and a run of constant children folds into one markup frame (§2.7). In the author's file, `out var` scopes all the way to the enclosing statement, so both shapes are valid C#. `LoweredHeaderLocalTests` pins Body-mode acceptance for every position above (lowered/native `if`, native `switch`'s discriminant and its own labels, `ForEach`/splice, and the native `foreach` iterator shape's own source expression, including its refused cross-sibling boundary and the iteration variable's separate symbol-identity exemption) alongside the refused boundary; `ViewPartTransplantTests` pins the same acceptance in ViewPart mode for the lowered/native `if`, `switch`, and `ForEach`/splice positions, plus the emission-path difference that mode alone exposes: a condition or discriminant designator is hole-ified there (also collected as a render variable, anchored on the same expression), while a `case` label's own designator is not anchored anywhere and keeps the author's spelling. The native `foreach` iterator shape's own ViewPart-mode acceptance is pinned separately, by `LoweredHeaderLocalTests`' own `RunIteratorViewPart` cases and by `ViewPartIteratorTests`' declaration-only sweep. The spliced expansion itself — that a call site actually compiles — is pinned by `ViewPartIteratorTests`' own `IteratorViewPart_WhenSplicedIntoAnElement_EmitsOneRegionAndOneStaticContentRange`/`..._ReusesTheContentRangeEveryIteration`, `IteratorViewPart_WhenTheYieldedElementCarriesKey_EmitsSetKeyOnItsOwnFrame` (each asserting `AssertOutputCompiles`), and `IteratorViewPart_WhenCalledTwice_NamesEachExpansionsIterationVariableApart`, which additionally confirms two expansions of the same iterator part name their loop variables apart rather than colliding.

**Opaque (runtime evaluation)**: a call to a `View`-returning method with no `[ViewPart]`, an indirect call through a delegate, and so on. The SG cannot analyze the inside, so it transplants the call expression into generated code and renders, at run time, the `RenderFragment` the returned `View` wraps. Notified by diagnostic BCF2001 (Info).

This path rests on one premise, and that premise decides its scope: the only spelling that puts a fragment into a `View` is `implicit operator View(RenderFragment?)`, and every member of the design-time surface returns a default value (§3.2). So a `View` built from the surface carries no fragment, and putting it on the Opaque path still renders nothing. When the call target's source declaration is in the current compilation and its body references the design-time surface, this does not fall onto this path — BCF3030 (Error) stops it instead. What is accepted as Opaque is a body that does not reference the surface, and a declaration that cannot be read. The latter carries residue that cannot be judged, recorded in Appendix A's BCF2001 row.

Accuracy is preserved at every tier. What is lost is only the static-diff optimization inside a Transplantable/Opaque region.

### 2.4 Static sequence-space separation for conditional branches

For SSC-2's `If`, a disjoint static sequence range is reserved for each branch:

```
If(condition, then: T₁, otherwise: T₂)

Assignment:  seq(boundary region)  = k
             seq space(T₁)         = [k+1,  k+1+W(T₁))
             seq space(T₂)         = [k+1+W(T₁), k+1+W(T₁)+W(T₂))
```

Conceptual shape of the generated code:

```csharp
__b.OpenRegion(k);
if (condition)
{
    /* T₁'s frame sequence: seq ∈ [k+1, k+1+W(T₁)) */
}
else
{
    /* T₂'s frame sequence: seq ∈ [k+1+W(T₁), …) — does not overlap T₁ */
}
__b.CloseRegion();
```

When `condition` transitions `true → false`, `T₁` and `T₂`'s sequences never intersect, so the Blazor engine correctly detects this as "exclusive discard of the whole segment and fresh generation" rather than "rewriting the same slot" (which would carry over the wrong state). This satisfies Theorem 1's condition (1) in a way consistent with branch semantics — nodes in different branches are not semantically identical.

`ForEach` (SSC-3) expands into a `foreach`, assigning a single static sequence space to the template `content` and identifying identity across iteration instances with `SetKey(key(item))`. The division of responsibility — sequence carries "syntactic position within the template," key carries "data identity" — and the minimal patch under a list mutation are shown as input/output examples in §2.7(B).

### 2.5 Sequence-space separation via regions

A Transplantable / Opaque region `D` is wrapped in a region whose boundary carries a single static sequence:

```csharp
__b.OpenRegion(seq_D);           // seq_D was assigned statically
__b.SetKey(runtimeKey);          // for Opaque, a runtime key where needed
/* D's content */
__b.CloseRegion();
```

Because a Blazor region isolates its sequence space, `D`'s internal dynamism never propagates out to the surrounding diffing.

A native `if`/`else` (§2.3's second Transplantable shape, `EmitTransplantedIf`) follows this same boundary, but its interior differs from an ordinary Transplantable/Opaque `D`: every arm's content lands at the same sequence number `seq_D + 1` rather than a disjoint per-branch range, because only one arm ever runs. Each arm's content is drawn through a freshly synthesized `RenderFragment` lambda (parameter named `__builder`, shadowing the outer one — every `EmitXxx` method writes that literal name, so a different parameter name would target the wrong builder) rather than `ViewRuntime.FragmentOf`: that helper only works for a `View` that already wraps a real, author-written fragment, and an SSC expression's `View` is always its default value at run time and carries no fragment (BCF2001/BCF3030's premise), so wrapping it in `FragmentOf` would silently render nothing.

```csharp
__b.OpenRegion(seq_D);
if (condition)
{
    __b.AddContent(seq_D + 1, (RenderTreeBuilder __builder) => { /* then's content, emitted at 0 */ });
}
else
{
    __b.AddContent(seq_D + 1, (RenderTreeBuilder __builder) => { /* otherwise's content, emitted at 0 */ });
}
__b.CloseRegion();
```

A native `switch` (§2.3's third Transplantable shape, `EmitTransplantedSwitch`) follows the same boundary and the same per-arm emission (`EmitTransplantedArm`, shared with `EmitTransplantedIf`) for the same reason: only one section ever runs, so every section's content lands at `seq_D + 1` too. What differs is only the header and the need to close each section: a section's own `return` was read into its synthesized fragment rather than transplanted, so an explicit `break` follows each section's content — without it, falling out of that statement into the next `case` would be fallthrough, which C# rejects.

```csharp
__b.OpenRegion(seq_D);
switch (discriminant)
{
    case A:
        __b.AddContent(seq_D + 1, (RenderTreeBuilder __builder) => { /* section's content, emitted at 0 */ });
        break;
    default:
        __b.AddContent(seq_D + 1, (RenderTreeBuilder __builder) => { /* section's content, emitted at 0 */ });
        break;
}
__b.CloseRegion();
```

An `else if` link recurses into this same emission without opening a nested region — the whole chain shares the one boundary `seq_D` names.

### 2.6 Hot Reload compatibility

Development-time edits are classified by mapping them to .NET Hot Reload's (EnC's) edit classes.

A change to a `Body` expression or a `[ViewPart]` body appears as a method-body swap in the regenerated `RenderView`. A method-body update is an edit class EnC supports stably. Adding a new `[ViewPart]` method is a member addition to an existing type, likewise within the supported range. A rude edit, such as a change to the component class's signature, requires an application restart, the same as with a Razor component.

The semantics of the first render after a reload follow directly from §1.2. When an edit changes the syntactic-position mapping `π`, the old and new `σ(π(n))` generally no longer agree (condition (1) fails to hold), so the affected component's frame sequence is treated by diff detection as "exclusive discard and fresh generation." Because the component instance itself is retained, C# field state survives, while DOM-local state (focus, scroll position, and so on) is lost. This is the same semantics as editing a Razor file, and needs no additional specification.

The application path also rides on the Blazor standard. Because the generated code is an ordinary method on a `ComponentBase`-derived type, Blazor's own `MetadataUpdateHandler`-driven re-render-after-update mechanism works unchanged. This design's only tooling-specific dependency is the single point that the Source Generator re-runs during an edit session and its updated generated code is applied through EnC. Behavior can differ across Visual Studio / `dotnet watch` / Rider, so each environment needs its own confirmation. Appendix C shows the development-time fallback for a case where a specific environment is found not to carry a re-run through to EnC.

### 2.7 Input/output specification for the key transforms: decoration folding, lists, part reuse, static folding, frame decorations

This design turns on five transforms: the decoration chain, lists, `[ViewPart]`, static subtrees, and non-attribute frame decorations (plain element emission is not included here). At the same level of detail as §2.4's `If`, each one defines exactly which input turns into which generated code.

**(A) Folding a decoration chain. Input: a chain of decorations / Output: `class` folds, other attributes and events emit 1:1 frames**

A decoration method is statically composed into the owning element's attributes and events, and adds no wrapper node. `class` is special: however many `.Class` (or `.Attr("class", …)`) are chained, they fold into a single `class` attribute, producing no extra attribute frame. An attribute or event other than `class` (`.Href` / `.Attr` / `.OnClick` / `.On`, and so on) is each emitted 1:1 as its own independent attribute/event frame, and a duplicate binding of the same attribute or event is diagnosed by BCF3010. Three spellings reach `class`, and only two of them fold: `.Bind("class", …)` does not join the channel and emits its own attribute frame, so combining it with a decoration emits two `class` attributes — diagnosed by BCF3024.

```csharp
// Input (a design-time C# expression)
Button
    .Class("btn")
    .Class("btn-primary")
    .OnClick(() => Save())["Save"]
```

```csharp
// Output (generated code): the two .Class calls fold into one class attribute; .OnClick is its own frame
__b.OpenElement(k,   "button");
__b.AddAttribute(k+1, "class", "btn btn-primary");
__b.AddAttribute(k+2, "onclick", /* () => Save() */);
__b.AddContent(k+3, "Save");
__b.CloseElement();
```

This `Button`'s `FrameWidth` is 4 (`OpenElement` + the `class` attribute + the `onclick` event + `AddContent`). Chaining `.Class` any number of times never increases the frame width, but adding one decoration other than `class` increases the frame width by one. A wrapper-node approach (one that generates a dedicated wrapper element per decoration) would have each decoration increase the DOM node count itself, but this design composes every decoration into the owning element's attributes and events, so DOM depth never increases. This asymmetry is the basis for diff detection's sequence assignment staying stable as decorations pile up.

An event frame's value is a call to `EventCallback.Factory.Create`, with the handler expression transplanted into its argument. When `.On<TArgs>` resolved, its type argument is written out as `Create<TArgs>` (a written type argument and an inferred one are not distinguished — they are two spellings that resolved to the same overload, and writing out only one would translate the same call two different ways). The transplant site has no parameter that was giving the handler its type at the call site. Because `Create` is overloaded, without a type argument the method group cannot infer `TValue`, and a lambda argument with no type annotation binds to `object` — both become CS1503 inside a file the author never wrote, so the call site's type argument is written out as-is to keep inference off the path (#371). A spelling with no type argument (a bare `.On` and an event shortcut) has no type to write out, and stays plain `Create`. That every handler spelling this surface allows binds in the generated code is pinned by `HtmlDecorationGeneratorTests.On_WithATypeArgument_NamesItOnCreate`, which compiles the generated output.

The one exception to 1:1 is two-way binding. `.Bind` emits one attribute frame and one event frame, so this decoration's `FrameWidth` is 2. Writing an event modifier on a bound event adds one more per modifier (§2.7(A)'s event-modifier item). When the bound attribute is `value` or `checked`, it also calls `SetUpdatesAttributeName` once; since this takes no sequence argument, it adds no frame (it only records the attribute name to resynchronize into the immediately preceding attribute frame). It is limited to these two attribute names because the only thing the client returns is that element's own `value` (or `checked` for a checkbox) as `EventFieldInfo` assembles it. `RenderTreeUpdater` writes that value into the frame this call named. Naming any other attribute overwrites an unrelated frame on a form element, leaving the real attribute stale, and on a non-form element `EventFieldInfo.fromEvent` returns `null`, so the call itself is a no-op. Because the record target is the immediately preceding attribute frame rather than the element, placing two bindings on the same element leaves each keeping its own name, with no overwrite and no lost resync (measured). Any number of bindings may be placed on the same element; the model side also holds an element's bindings as a collection. A name collision is reported by BCF3010, and when the bound attribute is `class` and the same element also carries a class-channel decoration, BCF3024 reports it. This was once rejected by BCF3021, but that was withdrawn because its basis was wrong (Appendix B.5).

```csharp
// Input (a design-time C# expression)
Input.Type("text").Bind("value", "oninput", () => _name)
```

```csharp
// Output (generated code): two frames, the attribute frame and the event frame, plus the resync record
__b.OpenElement(k,   "input");
__b.AddAttribute(k+1, "type", "text");
__b.AddAttribute(k+2, "value", _name);                  // attribute frame
__b.AddAttribute(k+3, "oninput", EventCallbackFactoryBinderExtensions.CreateBinder(
    EventCallback.Factory, this, __value => _name = __value, _name));   // event frame
__b.SetUpdatesAttributeName("value");                   // takes no sequence argument
__b.CloseElement();
```

`CreateBinder` is written as a static extension-method call because the generated file carries no `using`, and Razor's instance syntax (`EventCallback.Factory.CreateBinder(…)`) would be CS1061. The same normalization is applied to an author-written extension method too (§2.2). In the shape that writes the setter explicitly, `(Action<T>)(setter)` fills the `__value => …` position. For an async setter, `RuntimeHelpers.CreateInferredBindSetter(callback: setter, value: <current value>)` fills it. Either shape passes the current value as `CreateBinder`'s last argument, and the frame count does not change.

`.Bind` never takes part in (D)'s static folding. Its value is a read of a field or property, so it can never be a compile-time constant. But it is not the value's non-constancy that stops folding — the predicate itself does. `StaticMarkupSerializer.IsFoldableElement` returns not-foldable for any element whose binding collection `ElementNode.Bindings` is non-empty. Leaving it to a value check would let this predicate produce, in principle, output where the binding silently drops and only a plain attribute remains.

A component-side `.Bind` carries none of this asymmetry. The derived `{name}Changed` and `{name}Expression` stack as ordinary parameter frames, so the frame width is two `.Param`'s worth, or three for a type that declares `{name}Expression` (the component frame-width formula at the end of (D) applies as-is). Nor is there anything corresponding to the element side's `SetUpdatesAttributeName`, since it is the bound-to component that owns the DOM, not this call site.

An event modifier (`.PreventDefault` / `.StopPropagation`, Razor's `@onwheel:preventDefault`) attaches to the immediately preceding event, and stacks one frame of its own right after that event's frame. Its name is `__internal_preventDefault_<event name>` or `__internal_stopPropagation_<event name>`, and its value is `bool`.

```csharp
// Input
Div.Ref(r => _el = r).On<WheelEventArgs>("onwheel", Zoom).StopPropagation().PreventDefault()

// Output
__b.OpenElement(k, "div");
__b.AddAttribute(k+1, "onwheel", EventCallback.Factory.Create<WheelEventArgs>(this, Zoom));
__b.AddAttribute(k+2, "__internal_preventDefault_onwheel", true);   // always this order, not the chain's order
__b.AddAttribute(k+3, "__internal_stopPropagation_onwheel", true);
__b.AddElementReferenceCapture(k+4, r => _el = r);                  // after the modifiers
__b.CloseElement();
```

Three points were decided about this shape.

First, this writes `AddAttribute` directly rather than calling the framework's `AddEventPreventDefaultAttribute`. Those two are not members of `RenderTreeBuilder` but extension methods on `Microsoft.AspNetCore.Components.Web`'s `WebRenderTreeBuilderExtensions`, and their contents are the identical `AddAttribute` call written here (measured). Calling them would pull that assembly into the shipped package's dependency set, unraveling the fine-grained references #23 chose and settling, as a side effect, a question #156 has not yet decided — so the name is written by hand instead. The cost is that a framework-internal name ends up in the generated code, and `EventModifierParityTests` buys that back: it reads the generated spelling from `RenderViewEmitter`'s constants and cross-checks it against the frame the extension method emits, so a change to the naming convention fails a test rather than becoming a silent no-op.

Second, what triggers emitting the call is not the value but whether it was written at the call site. Write nothing and nothing is emitted. Write `.PreventDefault(false)` and the call is emitted, consuming one sequence number, and the framework side drops the frame (measured). This is a straightforward application of the rule Appendix D already states for a constant `false` `bool`: the number attaches to the call that was issued, not to the frame that resulted. The value may be a runtime expression, handled the same way as `.Attr(name, bool)`.

"The immediately preceding event" refers to any decoration that writes an event — `.On`, an event shortcut, and `.Bind` alike. The two channels record no order relative to each other, so only the syntax can answer which was written later. The judgment walks the chain leftward, stepping over decorations that produce no event (`.Class` / `.Attr` / other modifiers), and asks which channel the first event-producing decoration it finds wrote to. The modifier attaches to the end of that channel. The answer matches the end because decoration classification parses its own receiver first: at the point a modifier is reached, only what was written to its left is on the node, and the nearest event-producing decoration to the left is the one most recently stacked onto that channel.

The binding-side output places the modifier after `SetUpdatesAttributeName`. Because this call records into the immediately preceding attribute frame, inserting a modifier between it and the bound event frame would put the resync attribute name on the modifier's frame instead (#370).

Third, position needs no new rule. A modifier is an attribute frame, so unlike the three in (E) it falls inside the attribute range. Since `AssertCanAddAttribute` refuses to place an attribute after a reference capture, it must come before `.Ref` — but the emitter already stacks the capture only after every attribute, event, and binding has been emitted (E), so this ordering is satisfied structurally. Whatever order the author writes the chain in, the output follows the order above.

`.Attrs(IReadOnlyDictionary<string, object>? value)` spreads a runtime dictionary of attributes onto the element (Appendix B.14, revised #387). Unlike every other decoration in this section it is emitted *first* among attribute-producing decorations — immediately after `SetKey`, before the class channel and before the plain attribute loop — regardless of where `.Attrs` was written in the source chain, because `RenderViewEmitter.EmitElement` fixes channel emission order by node structure rather than by chain order. This is what makes an explicit `.Class`/`.Attr` always win Blazor's last-frame-wins duplicate resolution over a same-named runtime key, and lets every dictionary key the chain does not otherwise write survive untouched. Like `.Key`, `.Ref`, and `.FormName`, this compiler models at most one `.Attrs` per element (a second is BCF3033) — not because `AddMultipleAttributes` itself forbids being called twice, but because nothing motivates representing two, and because the frame it produces genuinely is attribute-shaped, unlike the other three, BCF3033's reuse here is about the compiler's model holding one dictionary expression, not about the underlying builder call's kind. Unlike `.Key`/`.Ref`/`.FormName` it also stops the fold for the same reason those three do, not because it is a non-attribute frame — `StaticMarkupSerializer.IsFoldableElement` excludes it explicitly, since markup has no spelling for a runtime dictionary and folding would silently drop it. It consumes exactly one sequence number whatever the dictionary holds at runtime, or none at all when absent, so #234's rule — that frame width is a function of the decorations written, never of a runtime value — holds unconditionally.

Splat-first has a cost, named in #387's own argument: because `RenderTreeBuilder` never merges a repeated `class` — a splat-carried `class` and an explicit `.Class` are two independent same-named frames, and `CloseElement` keeps only the later one outright, not a join of the two — a caller can no longer override an attribute the receiving component's own body already writes explicitly. Concretely: a component call site writing `.Class("primary")` on a component that Blazor routes into `AdditionalAttributes`, forwarded via that component's own `.Attrs(AdditionalAttributes)`, loses `"primary"` entirely the moment that component's own body also writes `.Class("btn")` or `.Attr("class", …)` — the component's own decoration wins, unconditionally, which is the entire point of adopting this order. What the dictionary still contributes, unconditionally, is every key the component's own body did not itself write.

```csharp
// Input (a design-time C# expression)
Button.Attrs(extra).Class("btn")["Save"]
```

```csharp
// Output (generated code): the splat claims the lowest attribute sequence number, unconditionally
__b.OpenElement(k,   "button");
__b.AddMultipleAttributes(k+1, (System.Collections.Generic.IReadOnlyDictionary<string, object>?)(extra));
__b.AddAttribute(k+2, "class", "btn");
__b.AddContent(k+3, "Save");
__b.CloseElement();
```

`.Class`/`.Attr` also exist on `ComponentView<TComponent>` (#314), each emitting a plain `AddAttribute` on the component's own frame — the same call the element side uses, not `AddComponentParameter` — because Blazor routes any component-frame attribute whose name matches no declared `[Parameter]` into `[Parameter(CaptureUnmatchedValues = true)]`, and one whose name does match binds that parameter directly through the same call (measured). Unlike every other decoration in this section, these are declared as `ComponentView<TComponent>` instance members rather than `Decorations` extension methods, for a reason stronger than the style `.Key`/`.RenderMode`/`.Ref` already set: a `Decorations` extension sharing the name `.Class`/`.Attr` with the element-side overload measurably degrades Roslyn's error recovery for every *other* failed `.Class`/`.Attr` call in a body, on any receiver, turning a recoverable single-candidate type into an unrecoverable error type — measured directly, an unrelated `.Param` call several frames away in the same expression stopped resolving to a concrete method entirely once that second extension existed. A member never enters extension-method candidate collection, so it carries none of that risk, and the call-site surface is unaffected either way. These are emitted immediately after `SetKey`, before every `AddComponentParameter` call ((C)/(E) below), which satisfies `RenderTreeBuilder`'s frame-kind contiguity assertion the same way the element side's attribute range does; interleaving with `AddComponentParameter` does not throw either way (measured), but "before" needs no separate justification since it mirrors the element side. Unlike the element side, there is no class-channel folding here — `.Class` is sugar for `.Attr("class", value)`, and writing either twice is BCF3010, the same duplicate-name rule as any other attribute name on this receiver. A name that matches a declared `[Parameter]` case-insensitively is rejected earlier, at classification time, as BCF3042, rather than being emitted at all — `TComponent`'s declared parameter set is known at the call site, so unlike the attribute *value* (whose type this surface never guesses beyond `string`/`bool`), a name collision here is exactly the kind of thing `DESIGN.md` §4.1 says to verify rather than guess.

`Id`/`Type`/`Title`/`Role`/`Href`/`Src`/`Alt` exist on `ComponentView<TComponent>` too (#489), mirroring #314's resolution rather than reviving the rejected `Decorations`-extension shape: each is sugar for `.Attr(name, value)` with the name fixed by which member was called, routed through the same classification `.Attr` uses (`ClassifyComponentAttribute`) with the name supplied rather than read from an argument — the same relationship `.Class` already has to `.Attr` on this receiver. The set is exactly the seven names B.21 closes the element-side shortcut boundary at (Appendix B.21); #490's later, standard-derived element shortcuts were not mirrored here, since #489's scope is closing the asymmetry with `.Class`/`.Attr`, not reopening B.21's boundary decision for the component side. The BCF3042 collision guard applies identically.

`.Param` also has six overloads for an `EventCallback`- or `EventCallback<TArg>`-typed parameter (#492), mirroring `EventCallbackFactory.Create`'s own overload set rather than `.On`'s: `Param(selector, Action)` / `Param(selector, Func<Task>)` for the non-generic form, and for the generic one both `Param<TArg>(selector, Action<TArg>)` / `Param<TArg>(selector, Func<TArg, Task>)` and the argument-ignoring `Param<TArg>(selector, Action)` / `Param<TArg>(selector, Func<Task>)` — the shape a parameterless handler needs, e.g. Razor's own `OnValidSubmit="HandleCreate"`, where `TArg` is inferred from the selector alone since nothing in the handler names it. Unlike the generic `Param<TValue>`, which casts its value straight through, these wrap the handler in `EventCallback.Factory.Create` — the same call `.On`'s handler and `.Bind`'s derived `{name}Changed` are already wrapped in — built from the handler's own segments so a `[ViewPart]` parameter hole inside it survives substitution, and cast to `method.Parameters[1].Type` (the overload's own declared handler type) rather than a type rebuilt from the selected property, since none of the six overloads needs the invert-the-getter form `.Bind`'s change callback does. The resulting `ComponentParameter` carries a `null` `ValueTypeName`, the same encoding `.Bind`'s `{name}Changed` uses, so the emitter adds no further cast around it. An author's own hand-written `EventCallback.Factory.Create(...)` call still binds through the generic `Param<TValue>` unchanged — its value's static type is `EventCallback`/`EventCallback<TArg>` itself, not an `Action`/`Func<Task>` handler, so it never becomes a candidate for these six overloads.

```csharp
// Input (a design-time C# expression)
Component<Widget>().Class("primary").Param(c => c.Title, "hi")
```

```csharp
// Output (generated code): the attribute frame precedes every AddComponentParameter
__b.OpenComponent<Widget>(m);
__b.AddAttribute(m+1, "class", "primary");
__b.AddComponentParameter(m+2, "Title", (string?)("hi"));
__b.CloseComponent();
```

**(B) `ForEach`. Input: a list mutation / Output: the minimal patch under key matching**

`ForEach` (SSC-3) expands into a `foreach`, assigning a single static sequence space to the template `content` and identifying identity across iteration instances with `SetKey(key(item))`. Sequence carries "syntactic position within the template," key carries "data identity" — the two responsibilities are orthogonal.

```csharp
// Input
ForEach(_items, key: t => t.Id, content: item =>
    Div.Class(item.Done ? "task done" : "task")[Span[item.Title]])
```

```csharp
// Output (generated code): the template's seq stays the same across iterations; identity is the key's job
__b.OpenRegion(k);
foreach (var item in _items)
{
    __b.OpenElement(k+1, "div");                        // Div (content's root element): seq ∈ [k+1, k+1+W(content))
    __b.SetKey(item.Id);                                // ← attach "immediately after" opening the root element
    __b.AddAttribute(k+2, "class", item.Done ? "task done" : "task");
    __b.OpenElement(k+3, "span"); __b.AddContent(k+4, item.Title); __b.CloseElement();
    __b.CloseElement();
}
__b.CloseRegion();
```

In Blazor's `RenderTreeBuilder`, `SetKey` attaches a key to "the frame of the element/component currently open" (the same shape as Razor's `@key`). The key must therefore be emitted **immediately after** opening `content`'s **root element/component**. Calling it before `OpenElement` — while the parent is still a region — throws `InvalidOperationException: Cannot set a key on a frame of type Region.` at run time. It follows that `ForEach`'s `content` must **have a single element or component as its root**, because a key can only be placed on an element or a component. A shape whose `content` root becomes a region (a bare `if`/`ForEach`/`switch`, and so on) cannot take a key, and is notified by diagnostic BCF3003 (Error). `Html.Fragment` (wrapperless grouping) and `Html.Raw` (trusted raw HTML injection) fall under the same constraint, since neither opens a single element/component frame, and neither can serve as `content`'s root (BCF3003). A nested keyed list wraps the inner loop in a container element (e.g. `content: o => Div[ForEach(o.Items, …)]`) — the same constraint as Razor, where `@key` cannot be placed directly on `@if` and needs an element to wrap it.

This not-keyable judgment is made by one function, `KeyabilityResolver.ResolveRoot`, called both from the template-walking diagnostic pass (before static expansion) and from `ViewPartExpander`'s post-expansion re-check before it emits a `SetKey`: a keyable root is limited to an element or a component that does not already carry its own key. Because both call sites share the one implementation, they cannot drift apart the way two independently maintained switches could. `KeyabilityResolverTests` pins, per type, how each node type is classified.

`KeyabilityResolver.ResolveRoot` throws on an unknown node type, the same contract `RenderViewEmitter.EmitNode` and `ViewPartExpander.ExpandNode` carry: an unknown node type is caught early as a bug, never let to pass silently as "not keyable."

The only implementation that determines sequence width is emission itself. Each `Emit*` returns the cursor it advanced, and a sibling's starting position is that return value. So adding a new node kind means adding exactly one case, in `RenderViewEmitter.EmitNode`, and a missed case is caught by the exception.

What guards the sequence arithmetic is a property of the emitted text itself: whatever shape the tree takes, the sequence arguments appearing in generated code are a dense run of `0..N-1` in order of appearance, because every node kind always writes the number it reserved into the text. `If` reserves both branches and emits both; `ForEach` reserves the content width and emits content. A slot continues the outer flat counter, and `CloseElement` / `CloseRegion` / `CloseComponent` / `SetKey` consume none. `RenderViewEmitterSequenceTests` checks this against a corpus covering every node kind. A comparison against an independently computed width only looks at the total, so it would pass two offsetting errors and an overlap in `If`'s branch ranges — but this property catches both. This density, by the way, is a property of this implementation's assignment scheme, not a Blazor requirement; all Blazor requires is that a sequence number is stable relative to syntactic position.

`RenderFragmentContentNode` consumes exactly one sequence number always, regardless of whether the `RenderFragment?` is non-null. A sequence-consuming `AddContent` call is always required, and the region frame it opens exists only when the value is non-null.

Trace the output patch when the input mutates from `[A, B, C]` to `[X, A, B, C]` by a leading insertion. Because the template's sequence number is the same across every iteration and identity is carried by the key, Blazor matches keys `A, B, C` against the existing frames (preserving row state and the DOM subtree) and inserts only the one row for `X`. If the key were index-derived instead, position 0 would be misread as "A → X changed," position 1 as "B → A changed," and so on — every row would be rewritten and each row's local state (focus position, and so on) would be lost. Key carrying "data identity" and sequence carrying "template position" is what makes this minimal patch and state preservation hold at the same time.

**(C) `[ViewPart]`'s static inline expansion. Input: a part call / Output: direct expansion into a contiguous seq**

A `[ViewPart]` method call is inline-expanded, body and all, at the call site (§2.2's `ViewPartCall` case). Neither a method call nor a region boundary is generated, and the sequence number stays contiguous with the surrounding body. Arguments are transplanted as syntax.

```csharp
// Input
protected override View Body =>
    Div[Toolbar("My App"), Span["Body"]];

[ViewPart]
private static View Toolbar(string title) =>
    Div.Class("toolbar")[Span[title]];
```

```csharp
// Output (generated code): Toolbar is inline-expanded, and seq runs contiguously from 0
__b.OpenElement(0, "div");                              // Div (Body's root element)
//   ↓ start of Toolbar("My App")'s inline expansion (no region boundary)
__b.OpenElement(1, "div");                              // Div (Toolbar's body)
__b.AddAttribute(2, "class", "toolbar");
__b.OpenElement(3, "span"); __b.AddContent(4, "My App"); __b.CloseElement();  // the title argument, transplanted
__b.CloseElement();
//   ↑ end of Toolbar's expansion
__b.OpenElement(5, "span"); __b.AddContent(6, "Body"); __b.CloseElement();
__b.CloseElement();
```

A `[ViewPart]` call produces the same frame sequence and sequence range as writing its body directly at the call site. Neither runtime dispatch nor region isolation is involved. By contrast, a `View`-returning method with no `[ViewPart]` is treated as Opaque (§2.3): wrapped in a region, rendered at run time as a `RenderFragment`, and subject to diagnostic BCF2001. It is this static-expandability, not whether the attribute was attached, that separates the speed and trimming characteristics of part reuse.

A `[ViewPart]` whose body is the fourth Transplantable shape (§2.3, a native `foreach` ending in one `yield return`) is not inline-expanded this way: the number of iterations is a run-time fact, so a spread call to it (`[.. Rows(...)]`) instead reuses `ForEach`'s own emission path from (B) — one static content range, reused by every iteration a `foreach` runs, rather than a copy of the body pasted once per call.

```csharp
// Input
private sealed record Item(int Id, string Name);
private readonly IReadOnlyList<Item> _items = new List<Item> { new Item(1, "a"), new Item(2, "b") };

[ViewPart]
private static IEnumerable<View> Rows(IReadOnlyList<Item> items)
{
    foreach (var item in items)
    {
        yield return Li.Key(item.Id)[item.Name];
    }
}

protected override View Body =>
    Ul[[.. Rows(_items)]];
```

```csharp
// Output (generated code): one region, one static content range reused every iteration -- the same
// shape (B)'s ForEach produces, not (C)'s inline expansion
__b.OpenElement(0, "ul");
IReadOnlyList<Item> __bcf_arg_1_0 = _items;
__b.OpenRegion(1);
foreach (var __bcf_item_2 in __bcf_arg_1_0)
{
    __b.OpenElement(2, "li");
    __b.SetKey(__bcf_item_2.Id);
    __b.AddContent(3, __bcf_item_2.Name);
    __b.CloseElement();
}
__b.CloseRegion();
__b.CloseElement();
```

`Rows`'s own argument (`_items`) lowers to a typed local the same way an ordinary `[ViewPart]` call's arguments do ((C) above), ahead of the region it is read inside. `.Key(...)` is written on the yielded element itself, the same as any other element's key decoration — never threaded through a separate parameter the way `ForEach`'s own `key:` argument is, because a native `foreach` header carries no sibling argument slot to carry one. Omitting it emits no `SetKey`, the same as a declined `ForEach` key ((B) above). Because `Rows` must be `static`, like every `[ViewPart]`, its loop source can never be read from an instance field directly — it is always threaded in as a parameter, as `items` is here (Appendix B.26).

**(D) Folding a static subtree. Input: a run of siblings written entirely in constants / Output: a single `AddMarkupContent` frame**

A region made up only of elements and text whose values are compile-time constants is serialized into a markup string and emitted as a single `AddMarkupContent` frame. The unit of folding is **a run, not a subtree** — a maximal sequence of consecutive foldable siblings.

```csharp
// Input (a design-time C# expression)
Div.Class("doc")[
    H1["BlazorCodeFirst"],
    Nav.Class("toc")[A.Href("#design")["Design"]],
    Span[$"Section {Index}"],
    P["Attributes are written before children."]]
```

```csharp
// Output (generated code): the runs before and after the dynamic Span each fold into one frame
__b.OpenElement(0, "div");
__b.AddAttribute(1, "class", "doc");
__b.AddMarkupContent(2, "<h1>BlazorCodeFirst</h1><nav class=\"toc\"><a href=\"#design\">Design</a></nav>");
__b.OpenElement(3, "span"); __b.AddContent(4, $"Section {Index}"); __b.CloseElement();
__b.AddMarkupContent(5, "<p>Attributes are written before children.</p>");
__b.CloseElement();
```

A folded run's frame width is 1, regardless of how many elements, attributes, and text nodes the run contains. Adjacent static siblings merge into one frame whenever nothing dynamic sits between them. This unit — a run rather than a subtree — is a correction #142's measurement revealed: the substance of the reduction comes from a run of static siblings, not from individual static subtrees.

A wrapper element stays an element frame only when it has a child that cannot be folded. In the example above, `div` stays because it has a dynamic `Span` as a child — a markup frame carries complete markup, so an opening tag cannot be folded together with a partial child list. Conversely, when the whole subtree is foldable, the root's opening tag lands in the same string too, and a fully static `Body` collapses the whole component into one `AddMarkupContent(0, …)` frame. The Razor compiler emits the same shape under the same condition (in the frame comparison #140 cites, the diff started at frame 2 rather than frame 0 because that example's `div` had a dynamic child).

Note that foldability is a strictly narrower notion than SSC (§2.3). SSC classifies whether a sequence number can be assigned statically, while folding requires the node's **value** to be a compile-time constant. `Span[$"Count: {Count}"]` belongs to SSC, but is not eligible for folding because its value is not constant.

The set of foldable tags is an allow-list: curated tags ∪ void tags ∪ custom element names, minus `pre` / `textarea` / `iframe`, whose text is interpreted differently from an ordinary element. Blazor escapes a value passed to `AddContent` but not one passed to `AddMarkupContent`, so escaping text and attribute values becomes the serializer's own responsibility. `Html.Raw` is excluded from folding: it is already one frame, so folding it alone gains nothing, and mixing it into an adjacent run is dangerous (an unbalanced string like `Raw("<i>")` would, when the whole run is parsed in one pass, pull the following siblings inside the `<i>`).

On the client, a text frame reaches the DOM through `createTextNode`, while a markup frame is parsed by assigning `innerHTML` on a shared `<template>` element. Neither `dotnet test` nor bUnit exercises this distinction: bUnit parses a document string with AngleSharp and prerendering writes markup verbatim, so both see a folded and an unfolded output as equivalent even where the client would not. `CONTRIBUTING.md` §Build and test names the browser check that does.

A value is also not folded when it cannot round-trip through markup. Four cases are excluded: carriage return (CR), NUL, an isolated surrogate, and a leading U+FEFF.

Even when constant, **a value that is not a string is not folded** (#158), because the compiler cannot know the culture the formatting will follow (when and where formatting happens is Appendix E.2). `3.5` reaches the DOM as `"3.5"` under `en-US` and as `"3,5"` under `de-DE`, and the compiler cannot know which. Folding it would bake one of them into the markup, so the same value would become a different string depending on whether its surroundings happen to be static. The cost of this exclusion is one missed opportunity to fold.

There are two exceptions. A **constant `null`** — string or otherwise — is omitted entirely, attribute and all, by `AddAttribute`, so the markup side matches by writing nothing either. A **constant `bool`** has nothing to format, so markup can express both outcomes exactly (`true` becomes `name=""`, `false` omits the attribute entirely). This is why `.Attr(name, bool)` is the one non-`string` spelling (`DESIGN.md` §4.1 and #158). The class channel folds by concatenation, so it too accepts only constant strings here.

Appendix E carries the shape of the mismatch behind each of the four exclusions, the measurements backing the two exceptions, and the character classes swept out once agreement was confirmed.

A `ForEach`'s content root is never folded, because `SetKey` cannot attach to a markup frame (see (B)). What guards this is simply whether the emitting side passes a key to the content root — there is no separate predicate, so the two can never disagree. A run that would absorb only a single frame is also not folded, since that would only change the shape without reducing anything.

**Folding changes the code path, not the output.** The folded markup and what the element path writes out through `HtmlEncoder` are identical for `&` `<` `>` `"` (unsurprising, since that identity is exactly what DOM equivalence requires). So **an assertion over output alone cannot show that the folding path was taken** — a test like that keeps passing even if folding quietly stops working. What a test that checks folding must pin alongside the output is in `CONTRIBUTING.md` §Conventions the code must uphold.

**A component's scalar parameter passes its value typed.** `.Param`'s value is transplanted into `AddComponentParameter`'s `object?` argument, losing the target type it had at the call site. So the emitting side wraps the value in a cast to the type argument C# resolved for that call. The type is taken from the resolved type argument, not from the selected property's declared type, because C# already guarantees the value has been converted to that type argument, so the cast can never fail to bind inside the generated code. A reference type is always written out as nullable: the cast asserts nothing about null, and since the generated file carries `#nullable enable`, dropping the annotation would raise CS8600 for a value written as `null` (#377, pinned by `Param_WithNullLiteralValue…`). When the type cannot be resolved, no cast is written, and it is emitted with the same spelling as today (the same rule as `Component<T>()`'s type argument).

**A component's fragment slot**: a `RenderFragment`-typed parameter carries no scalar value — it carries a node tree. So it is stored in a channel separate from `ComponentParameter` (scalar): `ComponentSlotNode`. The emitted frame width is `1 + Parameters.Length + Σ(1 + the content's frame width)`; each slot consumes one `AddComponentParameter` call plus its content's width.

The sequence number inside the lambda continues the outer flat counter, creating no independent sequence space. A slot's frames belong not to the caller but to the **child component's own frame sequence**. BlazorCodeFirst's generator is always the side that emits `AddComponentParameter(seq, "ChildContent", (RenderFragment)(...))`. Whether the fragment is invoked directly is a question for the receiving component (hand-written or Razor-generated alike): whether it passes it on to `AddContent` or calls it itself. The former is isolated by a Blazor region; the latter opens no region, and our numbers end up adjacent to the host's own frames. Renumbering from 0 would collide with the host's low numbers, causing the component to be regenerated and losing state (measured). Continuing flat is strictly the safe side. This is identical to Razor's own behavior, and wrapping it in a region does not fix it either, since a region does not change adjacency within the host's own frame sequence.

**A generic fragment slot**: a `RenderFragment<TContext>`-typed parameter is received via `.Template`. When the name is `ChildContent`, a bracket also receives it, emitting the same thing as the spelling that ignores context. What is emitted is a two-tier expression: an outer lambda taking `TContext`, wrapping an inner lambda taking `RenderTreeBuilder`. The outer parameter is a discard `_` for a spelling that ignores context, or a generated name, `__bcf_context_<logical preorder number>`, for a spelling that reads it. The inner tier is identical to the non-generic slot.

```csharp
// Input (a design-time C# expression)
Component<Card>()
    .Param(c => c.Title, "t")
    .Template(c => c.HeaderTemplate, Span["heading"])
    .Template(c => c.RowTemplate, row => Span[$"Row {row}"])
```

```csharp
// Output (generated code): scalars first, then slots in source order, seq continues flat
// (the cast's type name is shortened here for display; it is actually written out with the global:: qualifier per §2.2)
__b.OpenComponent<global::T.Card>(0);
__b.AddComponentParameter(1, "Title", (string?)("t"));
__b.AddComponentParameter(2, "HeaderTemplate", (RenderFragment<int>)((_) => (__builder) =>
{
    __builder.AddMarkupContent(3, "<span>heading</span>");
}));
__b.AddComponentParameter(4, "RowTemplate", (RenderFragment<int>)((__bcf_context_3) => (__builder) =>
{
    __builder.OpenElement(5, "span");
    __builder.AddContent(6, $"Row {__bcf_context_3}");
    __builder.CloseElement();
}));
__b.CloseComponent();
```

The channel's emission order is scalar parameters first, in source order, then slots, in source order. A slot's content's sequence number simply continues the outer flat counter, creating no independent space (the same rule as the non-generic slot). In the example above, `RowTemplate` is named `__bcf_context_3` because its logical preorder number is 3, a different number from its own `AddComponentParameter`'s seq (4) — there is no guarantee the two agree.

The context's name is decided by the generated side; an identifier the author wrote never appears in generated code. The author's lambda parameter is recorded in the template as the same kind of **hole** as a `[ViewPart]`'s argument, and the generated name is spliced in at expansion time. The hole's position is decided at parse time from the parameter's `ISymbol`, so something that merely shares the spelling (a same-named field, a same-named variable an inner lambda redeclares) is never rewritten. `ISymbol` and `TextSpan`, though, stay closed inside this one parsing call — only the rewritten string ever crosses into the template. The generator's incremental model must be built purely from immutable, value-equal records, primitives, and strings; bringing in a symbol or a span would break the cache's equality check.

Two collisions running the opposite direction are also closed off: if the author declared a name of their own that happens to be `__bcf_context_*`, it is renamed to `__bcf_authored_context_*`, and wherever a generated parameter would shadow the author's own non-static member, `this.` is supplied.

**(E) Non-attribute frame decorations. Input: `.Key` / `.Ref` / `.RenderMode` / Output: a non-attribute frame placed after the attribute frames**

`.Key` (Razor's `@key`), `.Ref` (`@ref`), `.RenderMode` (`@rendermode`), and `.FormName` (`@formname`) are never composed into the owning node's attributes. They take part in neither (A)'s folding nor (D)'s static folding, and each falls to its own dedicated `RenderTreeBuilder` call. There are four decorations but five calls they fall to (`.Ref` splits by receiver). The five differ from each other in kind, and that difference directly decides the emission rules.

| Spelling | Call | Sequence | Frame | Attaches to | `null` |
| --- | --- | --- | --- | --- | --- |
| `.Key` | `SetKey(object?)` | consumes none | does not stack (writes the open frame's key field) | element/component | early return |
| `.Ref` (element) | `AddElementReferenceCapture(int, Action<ElementReference>)` | **consumes 1** | stacks | element only | — |
| `.Ref` (component) | `AddComponentReferenceCapture(int, Action<object>)` | **consumes 1** | stacks | component only | — |
| `.RenderMode` | `AddComponentRenderMode(IComponentRenderMode?)` | consumes none | stacks | component only | early return |
| `.FormName` | `AddNamedEvent("onsubmit", string)` | consumes none | stacks | element only | BCF3039 (empty/literal `null` only) |

The four that stack a frame must be placed **after every attribute, event, binding, and slot of their owning node has been emitted, and before the children**. `RenderTreeBuilder`'s `AssertCanAddAttribute` and `AssertCanAddComponentParameter` look at the kind of the immediately preceding non-attribute frame, and adding an attribute after a reference-capture, render-mode, or named-event frame has been stacked throws `InvalidOperationException`. Because a component's slot is also stacked as `AddComponentParameter`, "after the parameters" means after both scalars and slots. `SetKey` alone stacks no frame and only rewrites the parent frame, so it sits outside this rule, and — like a `ForEach` key — is emitted immediately after `OpenElement` / `OpenComponent` ((B)). On the element side, `.FormName` is emitted before `.Ref` when both are written; the framework accepts either order (`AddNamedEvent` only requires the current parent frame to be an element, `AddElementReferenceCapture` only requires coming after the attribute range), so this is a choice rather than a requirement, the same status the component side gives the render-mode/reference-capture order.

On the element side there is one more reason it must come before the children: Blazor's diff reads an element's reference-capture frame as part of the attribute range, so a capture placed after the children falls outside that range. On the component side, the order between the two is render mode first, reference capture second — this is a choice, not a requirement, since the builder accepts either order; the only basis is that there is no reason to place a different-kind frame ahead of the walk that returns the first `ComponentRenderMode` frame when the renderer looks for the call site's mode.

```csharp
// Input (a design-time C# expression)
Div.Class("tab").Key(tab.Id).Ref(r => _tab = r)[Span[tab.Label]]
Component<Editor>().Param(c => c.Text, _text).RenderMode(_mode).Ref(c => _editor = c)
```

```csharp
// Output (generated code)
__b.OpenElement(k,   "div");
__b.SetKey(tab.Id);                                       // consumes no sequence
__b.AddAttribute(k+1, "class", "tab");
__b.AddElementReferenceCapture(k+2, r => _tab = r);        // after the attribute, before the children; consumes 1
__b.OpenElement(k+3, "span"); __b.AddContent(k+4, tab.Label); __b.CloseElement();
__b.CloseElement();

__b.OpenComponent<Editor>(m);
__b.AddComponentParameter(m+1, "Text", (string?)(_text));
__b.AddComponentRenderMode(_mode);                         // after the parameters, consumes no sequence
__b.AddComponentReferenceCapture(m+2, __value =>           // after the render mode; consumes 1
    ((System.Action<Editor>)(c => _editor = c))((Editor)__value));
__b.CloseComponent();
```

A cast is needed on the component-side capture because the framework takes `Action<object>` while the surface takes `Action<TComponent>`. It is the `ComponentView<TComponent>` side that knows the type, so the generated side writes the cast rather than making the author write it. The cast to a delegate is needed to invoke, in place, the lambda written in the argument position — the same shape a synchronous setter binding carries for the same reason.

`.Ref` is the only one that increases `FrameWidth`. `.Key` can still move an element's frame count, though: because `SetKey` cannot be expressed in markup, an element carrying `.Key` becomes unfoldable, and even one written entirely in constants is not folded into (D)'s single frame — it emits its own frame sequence instead. The same holds for `.Ref`. A component is already outside folding's scope, so `.RenderMode` moves neither. The rule at the end of (D) — that it is emission itself which determines width — still holds here, and no independent width calculation should be added for these three.

Writing the same frame decoration twice on the same node breaks all four in a way that fails to match what was written. `SetKey` overwrites the parent frame's key field, so only the one emitted later survives; `AddComponentRenderMode` goes the other way — `Renderer.FindCallerSpecifiedRenderMode` returns the first `ComponentRenderMode` frame, so only the one emitted first takes effect; a reference capture stacks two frames, firing both Actions; and two `AddNamedEvent` calls leave two different assigned names both registered against the same form, an outcome nothing the author wrote chose between. None of these follows a priority the author wrote, so BCF3033 rejects it. The shape where a `ForEach`'s key collides with the content root's own `.Key` is a different reporting layer, and BCF3032 handles that separately.

**(F) Scoped CSS attribute emission. Input: an element's owning file's `.cs.css` scope / Output: a bare one-argument `AddAttribute` frame, mirroring Razor's own scoped-CSS emission**

Scope is a file-unit concept: `Foo.cs` pairs with a same-named `Foo.cs.css`, and the scope (`bcf-xxxxxxxx`) covers every class declared in that file, including more than one component sharing it. A `partial` class's other declaring file carries no scope of its own unless that file has its own `.cs.css`; `CssScopeRegistry.GetScopeOrDefault` looks the scope up by `SyntaxTree.FilePath`, so it is symbol-free and file-keyed by construction, not class-keyed.

`[ViewPart]` expansion does not extend a host's scope to what it expands. When `ViewPartExpander` inlines a `[ViewPart]` method's body into a caller's tree ((C) above), every element it produces carries the scope registered for the `[ViewPart]`'s own declaring file, not the host's. This is the same non-reachability Razor already gives a child component's internals without `::deep`, and it is the only interpretation a file-unit scope can coherently take: the markup a `[ViewPart]` produces was written in its own file, so its scope follows it wherever it is expanded.

Razor's own generated code, for the elements the SDK's own `ApplyCssScopes`/`RewriteCss` pipeline scopes, calls the bare one-argument `AddAttribute(seq, "b-xxxxxxxx")` exactly once per dynamic element, placed after the element's other attributes and before its children — a presence-only frame with no value, matching what a browser parses out of a bare attribute. An element folded entirely into markup ((D) above) instead embeds the scope directly as a bare attribute in the string. BCF mirrors both paths against the same two injection points: `RenderViewEmitter` emits the bare-argument call on the frame path, and `Generation.StaticMarkupSerializer` embeds the bare attribute on the folded path, each reading `ElementNode.CssScope`. On the frame path the call consumes one sequence number like any other attribute frame ((A) above); on the folded path it is one more attribute `StaticMarkupSerializer.WriteTo`'s caller must count as absorbed, the same accounting (D) already gives every other folded attribute.

BCF3041 (Appendix A) is the diagnostic side of this model: it reports a `.cs.css` file with no matching `.cs` file, and a file that declares only `[ViewPart]` methods still counts as a match, because that file's scope still reaches rendered output through every call site even though the file itself renders nothing.

## 3. Memory layout

### 3.1 The SSC path: zero intermediate representation

The SSC (and Transplantable) path's runtime shape is a straight-line sequence of `RenderTreeBuilder` instructions carrying static sequence constants. The generated form is the same as the Razor compiler's output: no intermediate object born of the UI description (an element tree, a builder, a `params` array) is ever created on the heap. The marker type `View` is an empty `readonly struct`, unreachable at run time.

This makes the SSC path's allocation profile equivalent to the equivalent Razor component's — a measured figure in `DESIGN.md` §7.1, not a prediction. What allocation remains comes only from Blazor itself: event-handler delegates/closures, `RenderTreeBuilder`'s internal frame array (reused), and temporary strings from interpolation (partially mitigated via the `ISpanFormattable` path).

### 3.2 The Opaque path: a `View` that wraps a fragment

Only on the Opaque path does `View` carry any substance. There, `View` is a lightweight handle that wraps a reference to a `RenderFragment`, and the heap allocation is confined to building that wrapped fragment — the same cost as hand-composing a `RenderFragment` (a measured figure in `DESIGN.md` §7.1, not a prediction).

```csharp
public readonly struct View
{
    internal readonly RenderFragment? Fragment;   // always null on the SSC path (unreachable)
    internal View(RenderFragment fragment) => Fragment = fragment;
}
```

`implicit operator View(RenderFragment?)` constructs this field. This is the only spelling under which `View` carries substance, and because every member of the design-time surface (`Html` / `ElementView` / `Decorations`) returns a default value, a `View` built from the surface never carries a fragment. This asymmetry is BCF3030's basis (Appendix A, Appendix B.11).

Because the generated code sits in the user's own assembly, it cannot read the `internal` field. There is exactly one path that reads it, `BlazorCodeFirst.CompilerServices.ViewRuntime.FragmentOf`, positioned the same way Razor's generated code calls `Microsoft.AspNetCore.Components.CompilerServices.RuntimeHelpers`. Emission is a single `AddContent(seq, RenderFragment?)` frame; no `OpenRegion` is written, since Blazor itself opens a region for the fragment in response to this call — the same behavior `RenderFragmentContentNode` relies on.

### 3.3 Folding a static subtree

For a subtree that does not depend on state (a fixed header, terms of service, and so on), the Source Generator detects nodes whose values are compile-time constants and serializes a contiguous range into one markup string. What remains at run time is a single `AddMarkupContent` call — no element, attribute, or text frame is emitted. Not only does value recomputation and reformatting never happen, the frame count itself goes down. §2.7(D) defines the unit and the conditions of folding.

For a part that was not folded, frame emission still happens every time, since Blazor's diff detection requires it. Across the whole component, the frame count splits: a constant number (one per run) for the static parts, and — as before — a number proportional to the node structure for the dynamic parts.

## 4. Event propagation and the concurrency model

### 4.1 Execution order and single-direction data flow

From a user action to the DOM update, execution proceeds in one direction, in this order:

1. **Event fires** (the browser)
2. **Dispatch**: dispatch to Blazor's `SynchronizationContext` completes
3. **State transition**: the update from `s_t` to `s_{t+1}`
4. **Frame-sequence generation**: `RenderView` runs, generating `r_{t+1}`
5. **Diff application**: `Δ(r_t, r_{t+1})` synchronizes the DOM

The point of this order comes down to one thing: state transition must precede frame-sequence generation (state transition → generation). This enforces single-direction data flow, meaning a state transition must never occur while `RenderView` is running. At the current source-level implementation, this corresponds to "no state mutation inside a design-time expression (`BodyComponentBase.Body` or `ChromeLayoutBase.Chrome`)", and a violation is diagnostic BCF3001. A deferred handler argument, such as a `Button`'s onClick lambda, is excluded, since it does not run during rendering and executes only after the event. Complete detection of a side effect reached through an arbitrary method call is not guaranteed (see §1.1's BCF3001 note). Equivalent verification for a `[ViewPart]` body is a candidate for future extension, and is not part of this initial contract.

### 4.2 Division of labor with Blazor's standard dispatch

Blazor already provides serialized dispatch onto the rendering thread via `SynchronizationContext` (and `ComponentBase.InvokeAsync`). BlazorCodeFirst does not replace this. What this library adds to the concurrency model is limited to the following two points.

First, static verification by the analyzer of §4.1's "state transition → frame-sequence generation" order (the Blazor standard has only a convention, with no enforcement mechanism). Second, `Interlocked`-based lock-free notification coalescing that merges multiple state-change notifications from an external thread into a single re-render:

```csharp
private int _renderPending; // 0 or 1

public void NotifyStateChanged()
{
    if (Interlocked.CompareExchange(ref _renderPending, 1, 0) == 0)
    {
        _dispatcher.InvokeAsync(() =>
        {
            Volatile.Write(ref _renderPending, 0);
            StateHasChanged();
        });
    }
}
```

In a Wasm environment (effectively single-threaded today), the CAS always succeeds uncontended, so the overhead reduces to a single branch.

### 4.3 Runtime Async (net11.0, conditional)

On the net11.0 target, Runtime Async (runtime-native async) reduces async event handlers' state-machine overhead and flattens stack traces. No code change is needed on BlazorCodeFirst's side; the benefit comes from switching the TFM alone.

## 5. WebAssembly and AOT compilation compatibility

BlazorCodeFirst eliminates runtime metadata analysis and dynamic dispatch. Every parameter binding (including `Component<T>().Param(...)`) goes through a static setter the Source Generator generates. `Param`'s expression argument is parsed by the SG purely to generate that setter; no expression tree (`System.Linq.Expressions`) is ever compiled at run time. **There are zero places where the generated code calls `System.Reflection` / `System.Linq.Expressions`.** On the framework side the generated code calls into, there are two paths that pass through reflection, and both sit inside the boundary this section draws further down (the contract runs only as far as the code this design itself generates): `ComponentProperties.SetProperties` for `Component<T>().Param`, and, when binding an enum, `BindConverter.ParserDelegateCache` (which pulls out `ConvertToEnum` via `MakeGenericMethod`, #307). The latter was measured to survive trimming (`TrimmedOutputTests`, cost in Appendix E.2).

Furthermore, because both the design-time expression (`BodyComponentBase.Body` or `ChromeLayoutBase.Chrome`) and the design-time API are unreachable at run time, the IL trimmer can remove them wholesale. The design-time API here means every member of `Html` and `Decorations`, and every member of the design-time inert types `View` / `ComponentView<T>` / `ElementView` (Appendix A, BCF3014). The UI description's source code contributes nothing to binary size — a property a code-first approach that evaluates at run time cannot get. The design is verifiable, with `TrimMode=full` and `ILLinkTreatWarningsAsErrors=true` enabled, by scanning for MethodDef via `System.Reflection.Metadata`. The trim tests check this for both a component and a layout (a derived type's `Body`/`Chrome`, and the base's abstract getter).

Compared with an equivalent configuration that uses reflection-based binding, this is projected (predicted) to cut the AOT-compiled Wasm payload size by roughly 20-30%. This prediction is to be replaced with confirmed figures from benchmarks across three configurations: (a) BlazorCodeFirst, (b) reflection-binding, and (c) plain Razor. Against plain Razor, the expectation is near parity.

What BlazorCodeFirst's trimming/AOT-compatibility contract covers extends as far as the code it generates itself (a reflection-free `RenderView`, the design-time API that is unreachable at run time, and the `ComponentView` builder) being removed by trimming. For component embedding via `Component<T>().Param(...)`, at the stage where parameters are applied at run time, the framework's reflection-based `[Parameter]` binder (`ComponentProperties.SetProperties`) becomes reachable. This falls under the Blazor SDK's own trimming profile, and is not BlazorCodeFirst's responsibility. The trim-test harness (`tests/BlazorCodeFirst.TrimTestApp`) is a plain console app carrying no Blazor SDK profile, so this one framework-side `IL2072` surfaces on its own — a suppression scoped to `ComponentProperties.SetProperties` alone (`ILLink.LinkAttributes.xml`) is applied for exactly that reason.

`Component<T>()`'s type argument falls, as a literal, into the generated code's `OpenComponent<T>`, so it must already be resolved by the time BlazorCodeFirst's generator runs. Because source generators cannot see each other's output, a `.razor` component **in the same project** never satisfies this condition, and is reported as BCF3012. A `.razor` component in a referenced project or a NuGet package resolves normally, so this constraint is confined to within the same compilation; a hand-written C# component is always available.

## 6. .NET 11 conditional formal definition: the closed-world `ViewNode` (reference specification)

On the net11.0 target, C# 15's `closed` modifier is used to define the Source Generator's internal representation — the set of UI nodes — as a closed discriminated union: a `closed record` base with a `sealed record` per node shape.

```csharp
#if NET11_0_OR_GREATER
public closed record ViewNode
{
    public sealed record TextNode(string Content, StyleSet Style) : ViewNode;
    public sealed record StackNode(Axis Axis, int Spacing, ViewNode[] Children) : ViewNode;
    public sealed record ButtonNode(string Label, ActionRef Handler, ButtonStyle Style) : ViewNode;
    public sealed record RegionNode(int Seq, KeyRef? Key, ViewNode Body) : ViewNode;
    public sealed record ComponentNode(TypeRef ComponentType, ParameterBag Parameters) : ViewNode;
}
#endif
```

Closing the world lets the exhaustiveness of the compiler's internal visitors (frame emission, dependency analysis, diagnostics) be verified at compile time — a missed case becomes a compile error under this repository's `TreatWarningsAsErrors` (`Directory.Build.props`) — and lets the type system guarantee `FrameWidth`'s (§2.2) totality. `closed` is implicitly abstract; it cannot be combined with an explicit `abstract` modifier.

> Note: confirmed against .NET 11 Preview 6 (built with `LangVersion=preview`; issue #117): this shape compiles, and a `switch` omitting a case raises CS8509. `System.Runtime.CompilerServices.ClosedAttribute` now ships in-box, so no project-side declaration is needed. An earlier draft of this sketch combined `closed` with C# 15's separate `union` feature; that combination does not compile (`closed` is not a valid modifier on `union`), and `union` — composing a closed set of existing, unrelated types — does not fit `ViewNode`'s per-case fields regardless. On the net10.0 target, the equivalent structure is approximated with a `sealed` class hierarchy plus an exhaustiveness analyzer.

## Appendix A: Diagnostic Catalog

### A.0 A constraint on the reporting path: a diagnostic that explains a compile error cannot be reported by an analyzer

csc does not run the analyzer driver against a compilation that contains a declaration-level error (CS0534, CS0246, CS0234, and so on). This is standard Roslyn behavior, because analyzers presume a valid symbol model. The Source Generator driver has no such gate, so diagnostics the generator reports coexist with declaration errors in the output.

This gives the rule that decides where a diagnostic must be implemented.

> **If a diagnostic's role is to name the cause of a compile error the author cannot resolve alone, the Source Generator must report it.** Implemented as an analyzer, the very condition that should fire the diagnostic is what stops the analyzer driver, making it unreachable in principle.

BCF1001 violated this rule (#76). A missing `partial` means `RenderView` is not generated, which always produces the declaration-level error CS0534, so BCF1001 as an analyzer could never be reported in a real build — the condition that should have been diagnosed was suppressing the diagnostic itself. BCF1001 has been moved to generator reporting. For the same reason BCF1003 / BCF1005 were generator-reported from the start, and are emitted alongside CS0534.

A side effect follows: **in a compilation that contains even one declaration error, every analyzer diagnostic for that project disappears, not only BlazorCodeFirst's own (this includes CA/IDE rules too)**. This is not a property specific to BlazorCodeFirst, but a non-partial component is the easiest way to fall into this pitfall, which is also why reporting BCF1001 immediately from the generator has value.

The current reporting path is: BCF3001 by `RenderMutationAnalyzer`, BCF3029 by `InertSurfaceAnalyzer`, and everything else by `BlazorCodeFirstGenerator`. The two analyzers can be analyzers precisely because the shape that fires them compiles. BCF3001 is a design-time expression that contains a state mutation, and BCF3029 is a design-time API written where nothing reads it; both pass type checking, so the analyzer driver runs. When adding a new diagnostic, decide first whether the shape that fires it compiles.

This section is not a documentation-only promise; a test pins it. `tests/BlazorCodeFirst.DiagnosticTests` builds each project under `tests/diagnostic-fixtures` with a real MSBuild build and checks, from the SARIF log, which diagnostic was reported where. Including the same CA1050-violating type in every fixture pins two facts at once: that analyzer diagnostics disappear from a compilation with a declaration error, and that they are reported from a compilation without one. Every descriptor in `DiagnosticDescriptors` must either be covered at this layer or be on the exclusion list with a reason.

The table in the next section is verified by the same test project. `DiagnosticTableTests` reads the A.1 table and cross-checks it against `DiagnosticDescriptors` in both directions. It fails if a descriptor exists with no matching row, and it also fails if a row exists with no matching descriptor, unless the reason it is specified ahead of implementation is recorded in `DiagnosticExpectations.DocumentedWithoutDescriptor`. That registration is swapped out for the descriptor at implementation time, and a missed swap is caught by a separate test as "an exception that lost its reason." The Kind column is also checked against the descriptor's `DefaultSeverity`, so changing a diagnostic's severity also means changing the table (a row with no descriptor is excluded from this check).

## Appendix B: Alternative Architectures Considered and Why They Were Rejected

**B.1 The Interceptor approach (C# 14)**: evaluate `Body` at run time, and replace each design-time API call site with a statically sequenced implementation via an Interceptor. Call-site replacement itself works, but this was not adopted, for three reasons. (a) Because it presumes run-time evaluation, no unified return type can be constructed for a decoration chain's composed type (C# has no opaque return type, and `ref struct` cannot convert to an interface). (b) `[InterceptsLocation]`'s location specifier is recomputed on every source change, making the build pipeline sensitive to location data. (c) Since this design's approach (whole-program generation) is available, partial replacement carries no advantage of its own.

**B.2 The runtime `ref struct` tree approach**: build elements as `readonly ref struct` on the stack, and recursively call `Render` at run time. This is effective at avoiding GC, but was not adopted, for three reasons. (a) There is no way to accept a variable number of children (`ref struct` cannot be stored in an array or `params`, and a generic overload has an arity limit). (b) It has the same return-type problem as B.1. (c) It is incompatible with caching a static subtree (`ref struct` cannot be stored in a field). This design's approach (direct emission via generated code) achieves the same zero-allocation property without strain on the type system.

**B.3 Deriving `ChromeLayoutBase` from `BodyComponentBase` and intervening in `SetParametersAsync`**: put a layout on the same base type as an ordinary BlazorCodeFirst component, pulling the `Body` parameter Blazor passes out inside `SetParametersAsync` and forwarding the rest to the base. This approach was initially chosen, but was withdrawn after implementing and running it confirmed it does not work. The only public means of forwarding the remaining parameters is `ParameterView.FromDictionary`, but its enumerator always returns a fixed `cascading: false`. As a result, `ComponentProperties.SetProperties` throws for a property that accepts only a cascading value (*"The property 'X' … cannot be set explicitly because it only accepts cascading values."*). The impact is not limited to `[CascadingParameter]`: because this check is keyed on `CascadingParameterAttributeBase`, `[SupplyParameterFromQuery]` fails for the same reason. Even `[CascadingParameter] Task<AuthenticationState>`, standard in the authentication template, becomes unreceivable in a layout. It also allocates a `RenderTreeFrame[]` per navigation. The adopted approach (`ChromeLayoutBase : LayoutComponentBase`) inherits `Body` under the exact name Blazor requires it by, and carries over the `[DynamicDependency]` trimmer hint attached to `SetParametersAsync` unchanged, so it never competes with the platform's own parameter wiring. Lesson: this design does not intervene in the platform's own parameter wiring.

**B.4 Co-generating a `~AsFragment` sibling method for a `[ViewPart]` method**: generate, for each `[ViewPart]`, a static method that returns `RenderFragment`, so an existing `.razor` file can embed a fragment of code-first UI as `@Widgets.StatusBadgeAsFragment(status)`. `DESIGN.md` §6.1 and an invariant in `CONTRIBUTING.md` originally promised this, but it was never implemented, and was withdrawn in #144, for four reasons. (a) The requirement this approach tried to satisfy is already satisfied at component granularity. There is no same-project restriction on naming a BlazorCodeFirst component as a tag from `.razor` — `site/BlazorCodeFirst.Site/App.razor` does exactly that — because what Razor resolves is the class name the author wrote, and the generated output is only `RenderView`'s body. (b) The generated sibling method would carry substance and so become callable from a referencing assembly, creating an exception in `[ViewPart]`'s boundary (§4.3, BCF1002) — that static expansion requires the declaration's source syntax and so is confined to the same compilation. The same attribute would then carry two faces at once — "a same-compilation mechanism expanded at the call site" and "a declaration that grows a public API" — making the split between `[ViewPart]` and `Component<T>()` inexplicable. (c) The implementation would newly require three things: a `partial` requirement on the containing type (absent from `[ViewPart]` today — `site/BlazorCodeFirst.Site/Pages/NotFoundContent.cs` is a non-partial `static class`); a diagnostic for a `~AsFragment` name collision; and handling for the useless sibling a `private` `[ViewPart]` would generate. It was also never verified whether a `.razor` in the same project could call the generated static method — this sits in the same "source generators cannot see each other's output" territory that produced BCF3012, and if it does not hold, this approach would only be usable from a referenced assembly, where the component path in (a) always wins anyway. (d) What it buys is only embedding at a finer, sub-component fragment granularity, and the alternative is a single class wrapped in `BodyComponentBase`. Lesson: the unit of reuse and the unit of interop are both the component, and `[ViewPart]` stays strictly a same-compilation splitting device.

**B.5 Rejecting a second `.Bind` on the same element with BCF3021**: if two or more two-way bindings appear on one element, make it a compile error even when both names are free. This was implemented and shipped in #71, then withdrawn in #162. The basis given was the claim that "`SetUpdatesAttributeName` records into the element, so a second binding overwrites the first's resync target." That claim was flagged as wrong in #71's own final review, but the flag was never resolved before the rule shipped anyway. What #162 measured: `SetUpdatesAttributeName` writes the name into the immediately preceding attribute frame, not the element. The generated code emits, per binding, an attribute frame, an event frame, and `SetUpdatesAttributeName`, in that order — so the "immediately preceding attribute frame" here is that binding's own event frame, and it is that same event frame `RenderTreeUpdater.UpdateToMatchClientState` reads back from. The write target and the read source are the same frame, and that frame differs per binding, so two bindings on the same element never break each other's resync (§2.7(A)). What remained was a choice between reconstructing a different basis to keep the rule, or dropping it. It was dropped, on the principle of `DESIGN.md` §4.1: this surface checks translation breaks, not validity, and there is no break behind two bindings. Blazor renders this shape correctly under ordinary diff detection, and a motivating case is real (a Web Component with two or more two-way properties, `DESIGN.md` §4.1). Since the same principle leaves Appendix D's measured residue unchecked, there is no position from which to reject a shape that breaks nothing. Withdrawal did not free up the number: if a reader who hit this error in a preview build later searches by number, a different rule must never wear the same name. Because `AnalyzerReleases.Shipped.md` is empty, `CONTRIBUTING.md`'s ban on reusing an ID does not reach this number, so `DiagnosticExpectations.RetiredIds` and `DiagnosticTableTests.RetiredIds_AreNeitherDeclaredNorDocumented` mechanically pin that BCF3021 returns to neither a descriptor nor Appendix A. Lesson: a diagnostic that rests its basis on a claim about platform behavior ships only after that behavior is measured. Shipping without resolving a flag against the basis leaves the flag unrecorded and only the rule standing.

**B.6 Expressing voidness via `ElementView`'s type**: have the curated helper for the 13 void-element tags return a `VoidElementView` that carries no indexer. `Img["child"]` would then become CS0021 instead of BCF3016, and the surface would never even offer a shape HTML has no place for. Three lineages in §4.1 take this path: Giraffe.ViewEngine's `XmlNode` has a `VoidElement` case, so `br []` takes one list while `div [] []` takes two. Falco.Markup splits into `ParentNode` and `SelfClosingNode`, writing `_hr [ _class_ "divider" ]`. TyXML encodes it into a polymorphic-variant content model. This was considered in #179 and not adopted, for four reasons. (a) What it buys is shape alone. Both are already compile errors today; BCF3016 carries prose written for exactly this mistake, while CS0021 says nothing beyond "cannot apply indexing." The surface becomes more readable, and the diagnostic becomes less. (b) The cost lands on `Decorations`. All 22 decorations take `ElementView` and return `ElementView` (`Decorations.cs`); preserving voidness through the chain would require either duplicating the whole set for a void type, or making the whole set generic through a self-referencing-constrained builder interface. Either is large, and lands on a file any new decoration is guaranteed to touch, so #156 and #178 each get more expensive. (c) The check does not go away. `Element("br")["x"]` reaches the same tag through the string path, where no type exists to change, so BCF3016 is needed either way — a type would cover only half of this check's curated side. §4.1 states that the two paths agree structurally because both fall to a single tag string before consulting the same table, and a type rule that covers only one path is the opposite arrangement. (d) The mirroring argument is weaker than it looks: the boundary `DESIGN.md` §4.1 draws is whether something is decidable from the tag alone, and voidness sits inside that boundary — the design deliberately keeps it out of the type's territory and treats it as the check's territory instead. This item is a record in the same sense as Appendix D; reconsidering it needs a reason the four points above have not already answered.

**B.7 A generation rule that pushes the class channel's separator onto each term**: emit each term as `((t) is { } __c ? " " + __c : "")`, having the term itself carry the separator. This was adopted in #177's design, then withdrawn before implementation on an external reviewer's flag: it increases allocation. A non-null term never produces an extra space in the first place, so for the most common shape — `.Class("card").Class(_variant)` — this goes from one allocation to two while buying nothing. `class` is the most frequently written attribute on this surface (#177), and its value being non-constant is ordinary. The same review also offered an alternative: fold a constant prefix into both arms of the conditional, `((t) is { } c ? "card " + c : "card")`. This is one allocation with no extra space, but when the first term is itself conditional there is no foldable prefix, so it fails to reach the residue of `.Class(a ? "card" : null).Class(b ? "active" : null)`. What was adopted instead is a `private static` join the generated class keeps for itself, which skips `null` terms at run time (#236). This reaches both residues, and for a spelling with only non-null terms it collapses to the same single `string.Concat` call as the concatenation operator. Measurement across three shapes confirmed the allocation before and after the change matches (`ClassChannelBenchmarks`). Lesson: for a rule whose value is only known at run time, building one place that decides at run time can cost less than branching on the generated spelling's side.

Whether to put that join on the generated class's side or as a single method, `JoinClasses(params ReadOnlySpan<string?>)`, in `BlazorCodeFirst.Runtime`, was revisited in #239 and measured on 2026-08-14 (`ClassChannelBenchmarks`'s join-site rows). The surrounding frame calls are identical between the two approaches, so only the join expression itself was measured. The single-method side's body used the fastest spelling that preserves the rule: drop the `null` terms, then join what remains. A spelling that weaves in the separator before concatenating reads and writes `2n-1` slots for `n` terms, making it slower at every arity — measuring against that spelling would only record the generated-class side's win rather than measure it. #239's prediction about allocation held: because the caller takes the `params ReadOnlySpan` argument buffer on the stack, the two approaches were equal across all five shapes (2 terms: 40 B; 2 terms with one `null`: 0 B; 3 terms: 48 B; 4 terms: 64 B; 4 terms with two `null`: 40 B). Time was not one-sided — the faster side switched by shape. The generated-class side wins for a 2-term shape (7.17 ns vs. 12.03 ns) and for any shape with a `null` term; that gap is large, 0.15 ns vs. 2.46 ns for two terms with one `null`, because the arity-2 ladder — two `null` checks and one `string.Concat` — inlines, and with one term `null` it simply returns what remains. The single-method side runs a body that walks and repacks the terms regardless of shape. It loses on 3 terms with no `null` (22.58 ns vs. 19.33 ns) and 4 terms with no `null` (26.80 ns vs. 21.96 ns), a gap of 14-18%. The generated-class side was chosen because the winning shapes are the ones actually written on this channel: #236's motivation for this rule was a conditional term — one that becomes `null` at run time — and that is exactly the shape the ladder is best at. `site/BlazorCodeFirst.Site` writes `.Class` at 160 places, none of them stacking two on the same element, and none of its 12 generated classes carries a join. What is paid instead, ongoing, is the three things #239 counted: the arity ladder, passing arity through `IndentedWriter.WidestClassJoin`, and per-type-argument instantiation for a generic component. The public-surface cost turned out smaller than #239's estimate: `BlazorCodeFirst.CompilerServices.ViewRuntime`, which the generated code calls into, already carries `[EditorBrowsable(Never)]`, so there is no cost of appearing in a consumer's IntelliSense. This decision bets on the distribution of arities; reconsidering it needs measurement that 3 or more terms with no `null` are ordinarily written.

**B.8 Layering an opinionated layout/component tier on top of the HTML core**: give a vocabulary like `VStack` / `HStack` / `Card` / `Modal` / `PrimaryButton` as an opt-in second package that expands into HTML primitives, implemented as functions that return a pre-classed element (`static ElementView VStack(int gap = 4) => Div.Class($"flex flex-col gap-{gap}");`). Considered in #74, not adopted, for five reasons. (a) Being a separate assembly does not answer `DESIGN.md` §4.1's rejection. What that rejection turns away is "the library carrying two answers for layout," not which assembly the second one ships in — a first-party package becomes the official answer the moment it exists. Documentation demonstrates it, and a new reader learns it before the HTML surface. And because `Card` never appears in the DOM as `Card`, it breaks the 1:1 correspondence §8 credits to being DOM-native (the accessibility tree, the CSS ecosystem, readability in DevTools). (b) This tier asks nothing of the framework. `VStack` above is a one-line static method on top of the existing surface, requiring no new mechanism on either the compiler or the runtime side. Shipping first-party something an author can write in a few lines in their own project means carrying a second public surface — with `PublicAPI.*.txt`, versioning, documentation, and a backward-compatibility obligation — while buying nothing. (c) It forces a choice of CSS framework. The class string above is a Tailwind utility. There are three options, and none of them works: depend on Tailwind (betraying, by choosing one on the author's behalf, §8's own claim that the CSS ecosystem can be used as-is); bring its own CSS (becoming a different product — a component library competing head-on with MudBlazor / Radzen / Fluent UI, where this library has no advantage); or emit only class names with no CSS (useless). (d) The example code does not even work: `$"gap-{gap}"` is interpolation, so it is invisible to Tailwind's content scanner and gets purged. (e) The name offers no escape. `BlazorCodeFirst.UI` reads as "BlazorCodeFirst's UI part," which is backwards — it implies the core is not the UI layer — and, more importantly, the name `BlazorCodeFirst.*` itself reads as the official answer regardless. The suggestive precedent is Elm: `elm/html` is the core, while `mdgriffith/elm-ui`, a layout vocabulary that replaces the whole HTML/CSS way of thinking, is third-party, carries its own name, and coexists alongside `elm/html` rather than layering on top of it. If this tier is ever built, that shape — its own name, its own repository, built *on top of* BlazorCodeFirst — is the honest position, and it agrees with `DESIGN.md` §9's treatment of peripheral ideas as "considerations for a separate product independent of the core design." #74 originally held this decision open pending the resolution of "a reusable wrapper cannot be passed content." Stripping away the vocabulary, the real demand left behind is a reusable, parameterized fragment of UI with no wrapper element and no runtime cost, and the mechanism for that — `[ViewPart]` — already existed, except a `View`-typed parameter was rejected by BCF1002 at the time. That landed in #176 (`SlotView` and `Slot`, `DESIGN.md` §4.3). Now that the precondition is in place, this decision is a rejection, not a hold. Reconsidering it needs a concrete case `[ViewPart]`'s content path cannot carry. Lesson: when a second vocabulary looks necessary, suspect first that the first vocabulary is missing a means of composition.

**B.9 Giving `View` an indexer and unifying parts to one return type**: have `View` itself carry a `params ReadOnlySpan<View>` indexer, and make `[ViewPart]`'s return type `View` alone. A part that takes content and one that does not would both return `View`, and `Card("x")[P["body"]]` would pass through `View`'s indexer. The motivation is to remove the burden of choosing between `View` and `SlotView` every time an author declares a part, reinforced by the observation that §4.1's lineages, without exception, carry only one return type. Considered on 2026-08-11, not adopted, for five reasons. (a) The reason other lineages get by with one type has nothing to do with the return type — it is that **the built-in element's child channel is an ordinary function parameter**. Giraffe.ViewEngine / Falco.Markup / Feliz.ViewEngine take a positional argument equivalent to `XmlNode list`. kotlinx.html uses a trailing lambda (`fun FlowContent.card(title: String, block: DIV.() -> Unit)`, returning `Unit` whether the part takes children or not). Plot uses an `@ComponentBuilder` closure (`struct NewsArticle: Component { var body: Component }`). In every case, a hand-written part need only declare one parameter of the same type to take on the built-in's own shape — there is no mechanism left to reproduce. This surface's child channel is an indexer, and in C# a method cannot grow an indexer on its own call expression; only a type can carry an indexer, so giving a part the same shape as a built-in element requires a type. Once §4.3 chose the bracket, a second return type is a consequence of that choice, not an item that can be re-decided independently. (b) The one precedent that shares this problem draws the same distinction. Of §4.1's lineages, only Oxpecker.ViewEngine has its child syntax as its own construct, and its CE members are defined not on a concrete type but as a type extension of the `HtmlContainer` interface — that is, it distinguishes "can take children / cannot" by type, and mapped into C# that is exactly the current arrangement: `ElementView` and `SlotView` (can) versus `View` (cannot). (c) A rule the type closes for free would move to a diagnostic. §4.3 lists three: a forgotten bracket (`Div[Card("x")]`), the positional-argument spelling #176 rejected (`Card("t", P["body"])`), and decoration. On top of these, `Div["a"]["b"]`, `Fragment(…)["x"]`, `Raw(…)["x"]`, and `If(…)["x"]` would all newly compile. Decoration alone is unaffected (a decoration extends `ElementView`, and adding an indexer to `View` never moves the receiver's type). The set of new diagnostics needed grows from BCF3025's one to four or six. Appendix B.6 rejected the opposite trade — adding a type to reduce checks — and this item pays the same exchange rate in the reverse direction. (d) At least one of those never reaches a syntax check. `var v = Card("x"); Div[v];`, unlike the inline `Div[Card("x")]`, gives no syntactic way to tell that `v` is the return value of a part with a slot. This design's analysis is syntax-driven, and it has already decided to give up outside SSC and emit BCF2001 instead (§5.3). A type follows a variable around, but a syntax check does not, so this path silently renders empty content even with a diagnostic written for it — newly creating, out of territory the type closes today, exactly the kind of unchecked residue Appendix D records. (e) The same person pays both sides of the trade. What is saved is choosing a return type once per part declaration, and getting it wrong is reported immediately at the declaration site by either BCF1002 (a `View`-returning declaration with a `View` parameter) or BCF3025 (a `SlotView`-returning declaration with no `Slot`). What is added is room, on the calling side, to silently receive broken rendering. Since the author pays both, this is not a trade between the library and the author — it is a trade of a cost that is always noticed for one that is not. Reconsidering it needs measurement that the spellings named in (c) and (d) do not actually occur. That a two-way choice of return type looks unnatural by C# convention is not that measurement (§4.1).

**B.10 Replacing `.Param`'s selector with a shorter spelling**: shrink the fact that `Component<T>().Param(b => b.Label, label)` makes the author write a lambda every time, purely to name a target. Considered in #170, not adopted, on 2026-08-11. First, there is one wall none of the candidates can clear: only a declaration the author wrote can be named at the call site. Because a source generator never observes its own output, a member generated per component (`StatusBadge.Of(label: "x")`, a generated `.Label(…)` extension method, a generated builder type) does not bind at its call site while the generator is running. And the failure is an ugly kind: a generated member in a referenced project resolves via metadata, so BCF3012's asymmetry — compiling for a component in a separate assembly, failing for one in the same project — reappears, in the direction BCF-to-BCF composition mostly uses. `Component<T>()` itself is not open to change either: `Div` needs no parentheses because it is a property, and C# has no generic property, so `Component<T>` cannot become one. What can move is only `.Param`'s side, and within existing C# syntax there are three candidates. (a) A string name, `.Param("Label", label)`. Consistency with the element side's `.Attr(name, value)` looks like grounds for it, but the argument runs backward: `DESIGN.md` §4.1 made the attribute side a string because the attribute vocabulary is open to begin with, with nothing to map as a closed set. A component's parameter set is declared and closed, and already typed. C# already checks the value's type for free today (measured — `.Param(b => b.Compact, 42)` is CS0029/CS1662), and a string name would mean rewriting that as a new diagnostic — the same shape `DESIGN.md` §4.3 rejected a marker type's named channel for: rebuilding, for a positional argument, what C#'s overload resolution already gives for free. It also breaks IDE rename, one of the two things `DESIGN.md` §1.4 names as this design's actual value. (b) An object initializer, `Component(new StatusBadge { Label = label })`. This keeps both type checking and rename, but constructs a real component instance inside a design-time expression. `DESIGN.md` §5.1 states that every design-time API instance is inert, and §1.3 states that no heap allocation occurs at run time in principle — both break. #68 (that writing a design-time API outside a design-time expression does nothing) also gets worse, since an expression that does nothing today would start truly allocating. (c) An initializer lambda, `Component<StatusBadge>(b => { b.Label = label; b.Compact = compact; })`. Of the three, the only one that keeps type checking, rename, and inertness all at once. Even so, it was not adopted, for two reasons. First, `.Param` does not go away: `.Bind` needs the selector to derive `{name}Changed` and `{name}Expression`, and the shape that reads `.Template`'s context has the argument itself as a lambda — neither can take an assignment form. So the assignment form would sit alongside `.Param` rather than replacing it, against `DESIGN.md` §4.1/§4.3's position that the same thing should not carry two spellings. Second, a check that is structurally closed today by `.Param` splitting bindings one call at a time would move to a diagnostic: a block body can contain a statement that is not a plain assignment, or an assignment to a property that is not `[Parameter]`, so BCF3005 (the selector is not a simple property selection) and BCF3006 (the target is not a settable `[Parameter]`) — which today see this as a syntax shape — would have to be reworked against a set of statements. And the repetition this approach tries to shrink already has a different answer: wrap it once in a `[ViewPart]`, and both `Component` and `.Param` disappear from the call site, with named and optional arguments available as-is (`DESIGN.md` §4.3) — the attribute is paid once per declaration, not once per call site. Reconsidering it needs a case a `[ViewPart]` wrapper cannot carry. That repeated lambdas look verbose by C# convention is not that case (`DESIGN.md` §4.1).

**B.11 Auto-applying `[ViewPart]` with no attribute**: treat any static method that returns `View` as subject to static expansion, regardless of whether it carries the attribute. The motivation is removing, at once, the effort of writing the attribute and the accident of forgetting it and silently falling to the dynamic path (§2.3 Opaque). Considered on 2026-08-11, not adopted, for four reasons. (a) The set that can be expanded is narrower than "a static method that returns `View`." As BCF1002 enumerates, it requires a body that reaches one `return`, being non-generic, having no `params` / by-reference / `ElementView` parameter, and a statically sequenceable body, among other things. Automating this means deciding how to handle what is left over when these conditions are not met, and there are only two branches. (b) Turning a declaration that does not meet them into an error removes the escape-hatch spelling `DESIGN.md` §5.3 deliberately keeps: the path where writing unanalyzable code without the attribute simply passes as dynamic content would vanish, and an opt-out attribute would be needed instead — the side that must annotate simply swaps, with no reduction in attribute count. (c) Silently dropping a declaration that does not meet them to the dynamic path turns a cost that is always noticed into one that is not. Per §2.7, expansion produces the same frame sequence as writing the body inline at the call site, while the dynamic path wraps it in a region and draws a `RenderFragment` at run time — allocation and static optimization both differ. Today, the moment an author writes the attribute they declare "this is meant to expand," and if it does not hold, BCF1002 reports it immediately at the declaration site. Automated, adding just one native `foreach` to the body would silently degrade performance — the same trade Appendix B.9(e) rejected. (d) The scope of eligible members would need to be decided separately: `Body` and `Chrome` are `View`-returning properties, and an instance method, a local function, and a lambda would all become candidates. The attribute closes this set on the declaration side today, and automation moves that rule onto the author's side to remember (`DESIGN.md` §4.1). As for the forgotten-attribute accident named as the motivation, it is real, but the answer is a call-site diagnostic, not making the attribute automatic. BCF2001 (Info) was originally planned for this, but implementation revealed the premise was wrong: the only spelling that gives `View` substance is `implicit operator View(RenderFragment?)`, and every member of the design-time surface returns a default value — so a `View` built from the surface never carries a fragment, and putting it on the Opaque path still renders nothing. What is lost is not an optimization but the output itself, which does not match what an Info describes. What answers it is BCF3030 (Error), which stops this whenever the call target's source declaration can be read; only the case where it cannot be read remains BCF2001's concern (#260). Even with this split, the trade in this item's (c) still does not hold: the author receives a diagnostic the moment the attribute is forgotten, and the silent-fallthrough path is confined to a call whose source declaration cannot be read. Reconsidering it needs a third branch that avoids creating the silent degradation in (c).

**B.12 Two alternatives for building children from a collection**: #172 considered both, and adopted neither. That Issue's work was to give a spelling for splicing a collection into a child list, and what landed there is `key: null` and its sugar, the spread `Ul[[.. proj]]` (§2.3 SSC-3).

The first was adding an indexer overload that takes `IEnumerable<View>`, so `Ul[proj]` could be written. Rejected for three reasons. (a) The spread form can already write the same thing, and it mixes with sibling children — an indexer cannot mix, since its one argument is the whole child list. (b) `Ul[proj]` does not state, at the call site, whether one child or a sequence of children was placed; `..` does. This is the same standard the same Issue used when it made key absence a written `null` rather than a default, and it is what `DESIGN.md` §4.2 asks for. (c) Adding a second spelling for the same thing is the trade `DESIGN.md` §4.1 rejects, and because the child channel has four faces (`ElementView` / `ComponentView<T>` / `SlotView` / `Fragment`), it would multiply by four rather than add one. The implementation added no runtime API at all. Reconsidering it needs measurement that the spread form is not actually written, or is not readable.

The second was collapsing an `IEnumerable<View>` spread other than `Select` down to Opaque (BCF2001) — the plan at the time #172 was filed. Rejected for two reasons. (a) `Div[[.. _views]]` is a read-back of a stored `View`, exactly what Appendix A's BCF1003 row names as "what remains." The singular form `Div[_view]` is BCF1003, so letting only the plural through as Opaque would invert the two — the plural becoming looser than the singular. (b) A field is not a call, so BCF3030 does not reach it; because a `View` built from the surface carries no fragment, the Opaque path silently renders nothing — the same unnoticed cost Appendix B.9(e) and B.11(c) reject. So a spread other than `Select` was left as BCF1003. Reconsidering it needs measurement that this shape is written only for a `View` that carries a fragment.

**B.13 Loading an attribute name into metadata and letting decorations be declared externally**: recognize a static extension method that carries an attribute name in an attribute argument as a decoration. The declaration would take the shape `[Decoration("hx-get")] public static ElementView HxGet(this ElementView e, string? value) => e;`, lowering at the call site into exactly the same shape as `.Attr("hx-get", value)`. Because the attribute argument survives in metadata, this crosses an assembly boundary — unlike `[ViewPart]` — meaning a published HTMX pack would actually work. Since what it lowers to is identical to `.Attr`, BCF3010, BCF3023, BCF3024, and §2.7(D) would all reach it without modification. Considered in #242, not adopted. First, `DESIGN.md` §4.1's reason for rejecting a typed decoration (`.Padding()`) does not reach here: as long as the attribute name is copied through as-is, this never becomes a vocabulary that forces relearning. It was rejected for three reasons instead. (a) What it buys is only less repetition. `.Attr("hx-get", url)` already emits the same attribute in the same frame, so no capability is lost by not having it. (b) The cost lands on the attribute channel. BCF3010 / BCF3011 / BCF3023 / BCF3024 already sit here, and this would add a declaration-shape contract plus a diagnostic to name a contract violation. The contract would require five things: static, an extension of `ElementView`, returning `ElementView`, a non-empty constant name, and a value confined to the three shapes `string?` / `bool` / none. It would also need a path to collect `[Decoration]` declarations from referenced assemblies into the inert set BCF3029 watches (every member of `Html` and `Decorations`) — without that path, a pack consumer writing `e.HxGet("/x")` outside `Body` would produce no output and get no diagnostic. #242 does not count this item. (c) The extension point becomes an enumeration with no rule (superseded by B.21 revisited, #490: the shortcut set is now rule-derived, not an enumeration with no rule — but reasons (a) and (b) above stand on their own and still reject this alternative regardless). That Oxpecker.ViewEngine ships HTMX / Alpine / ARIA as separate packages does not reach this decision: it builds its tree at run time, so a type extension that calls `attr` succeeds while teaching the engine nothing — there is no decision to open in the first place, so it is no precedent for one either. What that fact shows is demand: people write attribute packs when they are free, which is not a case that justifies a costly mechanism. A variant that inline-expands the body falls without needing consideration: IL carries no body syntax, so it cannot cross an assembly boundary, and a published pack cannot work (Appendix B.4, the same reason as `DESIGN.md` §4.3). Reconsidering it requires distributing attribute sets as packages to become a goal of this surface.

**B.14 Taking the tag name and attribute names as runtime values**: three shapes handled together. The first decides the tag at run time, `Element(GetTagName())`; the second builds the attribute name at run time, `.Attr($"data-{kind}", value)`; the third is a dictionary-spread of attributes, `.Attrs(IReadOnlyDictionary<string, object>)` (Razor's `@attributes`). Considered in #320 and #308, neither adopted, on 2026-08-14. First, what both Issues saw as the obstacle is not one. #308 held that "a spread cannot be statically sequenced because the number of attributes is a runtime value." In fact, `RenderTreeBuilder.AddMultipleAttributes(int sequence, …)` takes one sequence number for the whole dictionary and passes it to every attribute frame — however many there are, the sequence-consuming call happens exactly once, and no downstream node's number moves (measured, `AttributeSplatMeasurementTests`). The tag is the same: `OpenElement(seq, expr)` takes one static number, so this does not even need the region #320 cited #17 as precedent for. That region, though, does not reach an attribute: `OpenRegion` sets the builder's immediately preceding non-attribute frame kind to `Region`, and a following `AddAttribute` throws (measured, ibid.). What #17 changed was the cost of the element and content paths, not the attribute channel's cost. What decides this is the class channel, not sequencing, and it was rejected for five reasons. (a) Folding is translation, not a check. An invisible check can simply stay silent — BCF3028 already does exactly that, skipping the check entirely in a compilation with no correspondence table. Folding has no such option: the generator must choose the value's destination at compile time, and either choice can go wrong depending on the runtime value. Choosing its own frame means an element whose name turns out to be `class` at run time carries two `class` frames — on an element with no spread, this is the very output BCF3024 rejects, and states does not specify which one survives. On an element with a spread, the answer is decided, and it is the worse one: `CloseElement` resolves the duplicate and keeps only the later frame, so a folded `class` is not extended but erased (measured, ibid.). `.Class("card").Class(_variant)` drops both from the output the instant the dictionary carries a `class` key. The channel's rule is concatenation (#236, §2.7(A)), and a second rule — replacement — would sit right beside it, with a key nowhere written in the source deciding which one takes effect. (b) There is no way to choose the folding side at run time either: folding is compile-time text concatenation, and its destination changes the frame count (no increase if it joins the channel; one more if it becomes its own frame) — against #234's rule that frame width is determined purely by the number of decorations and never moves with the value, and, as above, there is no region open at an attribute position that could absorb the difference. (c) BCF3010 would stop being a rule about an element's output and become a rule about how a name happens to be spelled. What this diagnostic rejects is output that fails to match what was written. A spread makes duplication ordinary rather than exceptional — letting the caller override a default is the whole point of this mechanism — and Blazor resolves that duplication silently besides. The same kind of break becomes a compile error if two names are written, and a silent last-wins if one of them comes from a dictionary. (d) The name that appears in the output stops appearing in the source. This is exactly why #244 rejected `.Data(name, value)`: every attribute shortcut on this surface spells the attribute name it emits, verbatim, in the source (`DESIGN.md` §4.1). A runtime name completes that break. Neither `$"data-{kind}"` nor a dictionary writes the attribute name that appears in the output anywhere in the source. The physical cost is `site/`'s `data-theme-toggle`, which #244 cited: only searching connects the C#, the browser-side JS, and the Playwright selector. (e) The tag side touches neither the class channel nor the duplicate check, but what it loses is the same kind of thing. BCF3016 today structurally covers every element path, because both the curated helper and `Element` fall to a single tag string before consulting the same table (`DESIGN.md` §4.1). A runtime tag produces a tag string that table can never be consulted for. What Appendix D records is residue chosen after measurement; what a runtime tag would produce is a hole the surface newly opens. This is the same trade Appendix B.6 rejected — on the grounds that "a type would cover only half of this check's curated side" — with the direction simply reversed. And §2.7(D)'s static folding stops at that element besides. What the five points share is the quality of the cost. An author who writes this shape today receives BCF3009 or BCF3011 right where they wrote it, and rewrites it to a constant spelling. Open the path, and what they receive instead is output that silently lost its `class`, or a void check that was silently skipped — the same trade of a noticed cost for an unnoticed one that Appendix B.9(e), B.11(c), and B.12 reject. The scope of this decision is the element's attribute channel; the path that passes attributes into a component call (#314) is a separate question, and no class channel exists there. Reconsidering it needs a case a constant tag and a constant attribute name cannot carry. Wanting to write a wrapper that receives attributes as a dictionary is not that case: a known set of attributes can already be received as ordinary `[ViewPart]` parameters, so a case only arises when the set is known only to the caller.

**B.14 revisited (#387, 2026-08-19)**: the dictionary-spread leg above is superseded for the element's receiving side. The original argument measured only one emission order — splat after the class channel — and reason (a) rests entirely on what that order does: `CloseElement` resolves a duplicate name by keeping the later frame, so a splat emitted second silently erases a folded `.Class` value. The reverse order was never measured. Measured (`AttributeSplatMeasurementTests.SplatFirst_TheExplicitFrameWins_AndUnwrittenKeysSurvive`): with the splat emitted first, `CloseElement` keeps the later, explicit frame — `.Class("card")` survives, unreplaced — and every dictionary key the call site did not write (`id` above) survives untouched beside it. `CaptureUnmatchedValues` (#314) is the case this entry's closing sentence asked for: an attribute set known only to the caller, not a wish but the platform's own mechanism, and #314 leaves a Compose component that declares `[Parameter(CaptureUnmatchedValues = true)]` with nowhere to forward the dictionary it receives onto a native element. `ElementView.Attrs(System.Collections.Generic.IReadOnlyDictionary<string, object>? value)` is adopted on this basis, emitting `AddMultipleAttributes` before the class channel and before every other attribute-producing decoration, so an explicit decoration always wins and an unwritten dictionary key always survives — the frame position is fixed by `RenderViewEmitter.EmitElement`'s own channel order, not by where `.Attrs` is written in the chain, so no "must be written first" rule exists or is needed. Re-reading the original five reasons against this: (a) resolved by the order above. (b) resolved — no folding is attempted; a splat's frame count is exactly one whatever the dictionary holds (`AttributeSplatMeasurementTests.Splat_ConsumesOneSequenceNumber_WhateverTheDictionaryHolds`), so #234's rule that frame width depends only on the number of decorations, never their runtime value, holds unconditionally. (c) unaffected: BCF3010 is a compile-time-only check over constant names and structurally cannot see the dictionary's runtime keys either way, and because the splat always loses to an explicit decoration, the dictionary can never overwrite what BCF3010 protects. (d) narrowed rather than eliminated: a splatted name still does not appear as a literal on *this* element, but it traces back to the caller's own source at whichever call site populated `AdditionalAttributes`, unlike `$"data-{kind}"`, which traces to nothing — (d) remains the live reason the tag-name and attribute-name-as-runtime-value legs above still stand on, since neither has an equivalent traceability escape. (e) untouched: the tag-side stays rejected, and a splatted element's tag is still a compile-time constant (BCF3009), so §2.7(D) static folding is unaffected — only the attribute list gains a dynamic member. The component-call leg this entry's closing sentence carved out (#314) is addressed separately: `ComponentView<TComponent>` gains a `.Class`/`.Attr` channel of its own (not a dictionary splat — a single constant attribute, per #314's own scope), guarded by BCF3042 against colliding with a declared `[Parameter]`. What splat-first costs, stated plainly and not left implicit: `RenderTreeBuilder` never merges a repeated `class` under any order — a splat-carried `class` and an explicit `.Class` are two independent same-named frames, and the later one wins outright, never a join of the two — so a caller can no longer override an attribute the receiving component's own body already writes. That is the trade this decision makes, in exchange for the property B.14's original rejection demanded and did not have: nothing the component author wrote is ever silently lost.

**B.15 Declaring the curated helpers all in lowercase**: spell `div` instead of `Div`, `span` instead of `Span`, matching the helper name to the tag name down to the letters. Considered in #174, not adopted. First, C# itself is no obstacle: a measurement cross-checking `KnownSymbols.CuratedTags`'s 100 tags against C#'s 77 reserved words (#174, reconfirmed 2026-08-16) found zero collisions. The two HTML tags that are reserved words, `object` and `base`, are already in exclusion groups 4 and 1 for unrelated reasons (`DESIGN.md` §4.1). `select` and `var` are contextual keywords, valid as member names. So an all-lowercase set of helpers would work — but working is not the same as being desirable. The recommended form is the unqualified spelling via `using static BlazorCodeFirst.Html;` (`DESIGN.md` §4.1), and going all-lowercase would bring `a` / `b` / `i` / `p` / `s` / `u` / `data` / `map` / `time` / `label` / `form` / `input` / `output` / `source` / `select` / `var` into that scope — every one of them the ordinary shape of a local variable in C#. Where ScalaTags and Elm carry off this exact form, it works because those languages' default convention for a value is already lowercase, and the DSL is not competing with its host — in C# it would be competing. What it buys is only a letter-for-letter match, and nothing is lost by not having it: the current mapping (capitalize the first letter) is a bijection, and the inverse map is mechanical (`DESIGN.md` §4.1, `KnownSymbolsSyncTests`). This measurement's value is not opening up a spelling choice — it is removing capitalization from the list of the mirror's limits. What lines up as a limit is a shape that has somewhere to map on the HTML side with no image on the surface, and a bijection is not that.

**B.16 Having an element-side `.Bind` derive the attribute name and event name from the element**: let the author write `Input.Type("text").Bind(() => _name)`, having the generator derive the bound attribute name (`value` / `checked`) and event name (`oninput` / `onchange`) from the tag and `type`. Razor's `@bind` behaves this way, and doing the same would remove the appearance that the element side and the component side decide names differently. Not adopted — because the element side has nothing to confirm a guess against. On the component side, a guess is confirmed by looking up `TComponent`'s type symbol, and the confirmed result feeds BCF3020's rejection (`DESIGN.md` §4.1, **only guess what can be verified**). Doing the same on the element side would need to read the tag and `type`. The tag is a constant (BCF3009), but `type` is a decoration argument, which can be an expression. What Razor reads when it chooses `checked` over `value` for `type="checkbox"` is a markup literal, and this surface's `.Type(kind)` is not a literal. Defaulting to `value` for a non-constant `type` would create a path where a checkbox stays bound to `value`, never works, and gets no diagnostic — a failure Razor, which reads a markup literal, never has, and which this surface alone would create. A variant that derives it only when `type` is constant is no better: it catches the same mistake in some spellings and not others, exactly what `DESIGN.md` §4.1 gives as its reason for never guessing `.Bind`'s culture. So the element side does not guess, and takes both names from the author. The cost is only the length of the spelling, and one side of a mix-up needs no confirmation source at all, since BCF3019 already catches it. Reconsidering it needs a mechanism that can derive the name without error along the path where `type` can be an expression.

**B.17 Allowing `[ViewPart]` to be declared as an extension member**: place `[ViewPart]` in a classic `this`-parameter form (`static View Label(this string value)`), or inside a C# 14 `extension` block, so `"x".Label()` could be called. Considered in #203, not adopted, on 2026-08-09. Both spellings are BCF1002 today. Two reasons, neither a preference of spelling. (a) On this surface, a trailing `.Foo(...)` chain is reserved for decorating an element (`DESIGN.md` §4.1); `"x".Label()` would put something that is not a decoration there. The only call spelling `[ViewPart]` gives is the plain call, `AppHeader("My Application")` (§4.3, ibid.), and fluent would become a second spelling with no counterpart in HTML. (b) The receiver could never be a value of this surface: an `ElementView` parameter is rejected, and a `View` parameter is a content slot, never a receiver (both BCF1002). So an extension ViewPart could only ever be a tool for extending someone else's type's vocabulary — falling outside the position that makes the component the unit of both reuse and interop, with `[ViewPart]` strictly a same-compilation splitting device — the same shape as reason (b) behind Appendix B.4's withdrawal of `~AsFragment`. Reconsidering it needs a case a plain call cannot carry. That fluent looks natural by C# convention is not that case (`DESIGN.md` §4.1).

**B.18 Rejecting an event modifier that cannot reach a `.Bind`'s event with BCF3037**: make an event modifier written after `.Bind` a compile error, without resolving it. Implemented in #368, withdrawn in #370. Unlike B.5, the basis stayed correct — this was withdrawn not because the basis collapsed, but because what it was rejecting stopped needing rejection. What BCF3037 prevented was a break where a modifier silently attached to the end of the event channel and modified an event the author never wrote it for; this break is real, and with no rule there is no diagnostic for it either. What #370 changed was widening what the chain's backward walk answers, from "is this `.Bind`?" to "which channel was this written to?" The target is now decided by that same single walk, so the path to attaching to the wrong target vanished — and with it, the thing there was to reject. The number is not reused (`CONTRIBUTING.md` §Conventions the code must uphold).

**B.19 Checking whether an attribute may be applied to a given element**: report `Div.Href("/x")` / `Div.Attr("href", "/x")` as invalid, since `div` does not take `href`. Considered in #335, not adopted. #129 once placed one of its reasons on "the attribute vocabulary is open, so `.Attr` cannot be covered," but that is wrong: an open vocabulary means an unknown name cannot be judged — it does not mean a known name cannot be. BCF3009 already requires the tag, and BCF3011 the `.Attr` name, to each be a non-empty compile-time constant, so both spellings fall to the same pair, `("div", "href")`, and one table can answer for both — the HTML Living Standard's *Index — Attributes* and its `Element(s)` column, a table the standard already ships as canonical, the same as the curated set and the void set. So the boundary about whether checking it would commit this repository to authoring a table does not exclude this check; what excludes it is the condition that comes before that. Static SSR and interactive rendering both emit `<div href="/x">` for `Div.Href("/x")`; it matches what was written, and the translation is not broken. What this surface reports is a shape that fails to match what was written. Reporting a shape that matches what was written but is meaningless as HTML would mean introducing a second axis — validity — and that is exactly the kotlinx.html-style position `DESIGN.md` §4.1 states this design does not take. Appendix B.5, which withdrew BCF3021, followed the same logic: since Appendix D already leaves measured breaks unchecked, there is no position from which to reject only a shape that breaks nothing. The question of severity sits downstream of this axis, so introducing no new axis means no occasion to choose Warning arises either.

**B.20 Prefix-composing shortcuts for `data-*` / `aria-*`**: add `.Data(name, value)` and `.Aria(name, value)`, composing the prefix rather than requiring the author to write it. Considered in #244, not adopted. Every attribute shortcut on this surface copies the attribute name straight through (a necessary condition since B.21 revisited, #490, and true of the seven that existed when this decision was made), so the name appearing in the output also appears in the source. `.Data("sku", …)` would become the first member to break that: the completed name, `data-sku`, would never be written anywhere, and would have to be traced from outside C#. `site/`'s `data-theme-toggle` appears, in the identical spelling, at three places — `.Attr` in `SiteNav.cs`, the browser-side JS, and a Playwright selector — and only searching connects the three. It does not remove the curated/general split either (`DESIGN.md` §4.1): because `data-*` and `aria-*` are both open namespaces, the curation #99 did for elements never applies here, so this would become a shortcut for syntax rather than for a name. There is also already `Html.Data`, the curated helper for the `<data>` element; overload resolution would not split, but `Data.Data("kind", "price")` would become writable — `<data value>` is the element for a machine-readable value, and `data-*` is the attribute family that hangs off it, so a scene with both on the same element is not contrived. `.Attr("data-sku", …)` has neither problem. Reconsidering it needs measurement that `.Attr`'s spelling is an actual obstacle.

**B.21 Where the seven attribute shortcuts' boundary sits, and why an eighth was not added**: `Href` / `Src` / `Alt` / `Id` / `Type` / `Title` / `Role` share three traits — each spells the attribute name it emits verbatim (#244), each value is a single opaque string, and each emits exactly one attribute frame. These are necessary conditions, not sufficient ones: `for` / `value` / `name` / `placeholder` / `lang` / `dir` / `tabindex` all satisfy them too. Frequency gives the candidates an order but not where to cut, so no rule can be written to turn away an eighth. For the element vocabulary, a rule could be written, because the standard's own index ships a closed set, and writing the exclusion reasons as six groups automatically decides the rest (`DESIGN.md` §4.1). The attribute vocabulary is open, and there is no closed set to map into. What decides this set's boundary is not a rule but history, and the decision (2026-08-14, #321) is simply not moving that boundary. The cost is limited: an attribute with no shortcut still emits through the same frame via `.Attr(name, value)`, so no capability is lost. Adding one needs measurement that `.Attr`'s spelling is an actual obstacle.

**B.21 revisited (#490, 2026-08-20)**: the boundary above is superseded. B.21's original argument found three necessary conditions the seven share — each spells the attribute name it emits verbatim, each value is a single opaque string, each emits exactly one attribute frame — and concluded no rule decides where an eighth stops, so the boundary was left as history. That conclusion followed from treating the three conditions as a search for a cutoff. Read them instead as a membership test with no cutoff: every entry in the HTML Living Standard's *Index — Attributes* meeting all three qualifies, the same way `DESIGN.md` §4.1 already reads the standard's element index by rule rather than by enumeration. Applying the test to the standard's attribute table (fetched and parsed 2026-08-20) yields 142 qualifying names; six were already implemented (`Href`/`Src`/`Alt`/`Id`/`Type`/`Title`), and 136 are new. Boolean-valued entries — traced from the standard's Value column, 30 in total (`disabled`/`checked`/`hidden`, and the rest) — get one method taking `bool`, mirroring `.Attr(name, bool)`'s shape; none needs `.Attr`'s bare/conditional two-overload split, because that split exists only to break a tie between two overloads sharing the `Attr` name (RS0027) — a named shortcut has no sibling overload to tie with. `role` is excluded from the derivation: it is defined by WAI-ARIA, not the HTML Living Standard, so it has no row in the table this rule reads, and it stays the one hand-picked entry in `AttributeShortcutNames`. `class`/`style` are excluded because they already have their own channel (§2.7(A), B.22). `data-*`/`aria-*` remain excluded (#244/B.20 unchanged) — open namespaces with no row in the standard's table to read. None of this reopens B.19/#335: every generated shortcut is still writable on any element, exactly as `Href`/`Src`/`Alt` already were, so the checked/unchecked boundary — translation break, not HTML validity — does not move; reaching that would need either a per-element receiver type (rejected on the same grounds as B.6, at a much larger scale) or reviving the diagnostic #335 rejected, and neither has new evidence behind it. A few generated names collide, harmlessly, with existing curated element helper names (`Abbr`/`Cite`/`Data`/`Form`/`Label`/`Span` are both an `Html` element property and a `Decorations` method); the two live in different receiver scopes (`Html.Data` vs. `element.Data(...)`), so nothing fails to compile — `Data.Data("kind", "price")` is an odd-looking expression, not an incorrect one.

**B.22 A `.Style` channel for the `style` attribute**: give `style` a channel like `class`'s, so `.Style("color:red")` concatenates across decorations instead of colliding. Considered in #321, not adopted. `style`'s value is a sequence of declarations, and `class` is the only other sequence-valued attribute on this surface, which already has a channel. The rule for `.Style` would have to be one of two. Choose a rule that does not fold, and `.Style("color:red").Style(cond ? "display:none" : null)` becomes BCF3010 — under a CSS reading both would survive, so the two sequence-valued attributes would answer the same spelling in opposite ways. Choose a rule that does fold, and a second channel appears, separator `;`. The class channel already carries three rules (the concatenation generation rule drops a `null` term, #236/Appendix B.7; BCF3023 rejects `bool`; BCF3024 watches for coexistence with `.Bind`), all written under the name `class`, and a second channel would duplicate all three, per name. Either rule buys only shorter spelling, and `.Attr("style", …)` still emits the same attribute frame regardless. So `style` is not folded and carries no channel: placing `.Attr("style", …)` twice on the same element is BCF3010, the same as every name other than `class`. Before this decision, the sentence rejecting the layout vocabulary (`DESIGN.md` §4.1) also removed a `style` shortcut along with it, on grounds that were a preference about CSS methodology (recommending classes over external CSS) rather than about the channel question above. An inline style is valid HTML, and Blazor draws it correctly; for the same reason a shape that breaks nothing goes unchecked, this surface does not decide the rights and wrongs of how something is written. The exclusion stands, but its grounds moved here.

**B.23 Widening `Body` to a statement body, for native `if` / `foreach` with full static assignment**: let a design-time expression's getter be a statement body, so `if` and `foreach` could be written directly instead of through `If` / `ForEach`. Considered on 2026-08-11, not adopted (#175). As long as the channel for passing children is the bracket, making room for a statement would mean swapping the child channel for a lambda block, which stops mirroring how HTML writes children inside a tag. It also does not remove `If` / `ForEach` anyway: a plain `foreach` has nowhere to place a key, and a statement cannot be placed where an expression is required, so an approach meant to remove the two would add to them instead, without removing anything. This is not §5.3's native control construct, which is a degradation to a dynamic region that preserves correctness but gains no static assignment — what was considered and rejected here is an approach aimed at removing that degradation entirely. Reconsidering it needs measurement that `If` / `ForEach` are an actual learning obstacle.

**B.24 Using ExCSS (nuget.org) to parse and rewrite `.cs.css` in place**: parse each stylesheet with `ExCSS`'s `StylesheetParser` and use its parsed nodes' position information to apply the same position-preserving edits dotnet/sdk's `RewriteCss.cs` makes (insert `[scope]`, insert `-{scope}` into a `@keyframes` name, delete a stripped `::deep` token) at their original offsets in untouched text. Verified against `ExCSS 4.3.2` in a throwaway project (no change to this repository); not adopted. `Microsoft.Css.Parser`, the parser `RewriteCss.cs` itself is built on, is not published to nuget.org — only to an internal dnceng feed with no version or availability contract — so it was never a candidate, and dotnet/sdk's own `RewriteCss.cs` is coupled deeply enough to that parser's AST that adopting any other parser costs about the same rewrite regardless of which one. Three measured limits rule ExCSS out specifically. Position information (`StylesheetText.Range`) is attached only to a whole `StyleRule` or a whole comma-separated selector list, not to an individual selector component or declaration — too coarse for `RewriteCss.cs`'s core moves, which need to insert immediately before a pseudo-element or delete only a `::deep` token. The parser also reinterprets values on the way back out: `animation: my-animation 1s infinite` expands into its eight longhands with `initial` filled in for the ones left unwritten, and `color: red` becomes `rgb(255, 0, 0)`. Comments are dropped from a selector list's `ToCss()` even with `preserveComments: true`. Full-document re-serialization cannot reconcile with these three at once, and `RewriteCssTest.cs`'s fixtures require a byte-for-byte match against the original text outside the edited spans — the reason `ScopedCssRewriter` instead hand-rolls a position-tracking scanner over the original text and applies every edit as an absolute offset in one left-to-right pass.

**B.25 Dependency tracking for the `ComponentModeling` pipeline (#480)**: pre-link which component calls which view part, so an edit to one view part's `[ViewPart]` definition only reruns `ComponentModelFactory.Expand` for the components that actually call it, instead of every component in the compilation. Considered in #480 (2026-08-19), not adopted. Roslyn's `Combine` compares `registry`/`cssScopeRegistry` as whole values against every one of the N `analyses` entries in `BlazorCodeFirstGenerator.cs`'s `modelResults` pipeline, so any change to either — including an offset-only edit that only moves a `TemplateLocation` — reruns `Expand` for all N components; `EquatableArray` value equality still keeps unrelated components' generated output `Unchanged`, so correctness holds (`IncrementalGeneratorTests.IncrementalGenerator_WhenViewPartDefinitionChanges_InvalidatesOnlyDependentCaller`), but the CPU cost scales with N regardless of relevance. `RegistryBroadcastCostTests` (#483) measured the wasted cost at N=10/100/1000: 0.12ms/13.11ms/88.10ms above an unrelated-file control edit (Release, 5-trial median) — negligible at the component counts this project has today, non-negligible only once N approaches four figures. Reopening this needs the same kind of measured evidence, taken at the scale it would apply to: once a project's component count approaches N≈100–150 (the figure issue #480 tracks), remeasure with `RegistryBroadcastCostTests` before deciding whether to build dependency tracking — or a cheaper alternative floated in #480 but not yet designed or measured, comparing each component's own reachable subset of `registry`/`cssScopeRegistry` entries instead of the whole collection.

**B.26 Alternative spellings for a `[ViewPart]`'s native `foreach` (#316)**: two conclusions this investigation settled once the fourth Transplantable shape (§2.3) was designed, recorded here because neither is visible from the shipped shape alone. First, whether some spelling other than a C# iterator could serve. A `foreach` ending in `return <expr>;`, mirroring how the second and third Transplantable shapes end in `return`, was the obvious candidate and does not work: returning inside a loop body exits after the first item, which is not "produce every item," and C# then requires a further `return` after the loop or reports CS0161 ("not all code paths return a value") — there is no `return`-based spelling that both compiles and means what a repeated-child loop needs to mean. `yield return` is the only C# construct whose meaning is "produce a value per pass through a loop, and keep going," but expressing that meaning requires the enclosing member to be a genuine iterator, which only a method can be — CS1624 rules it out for a property getter, CS1621 for a lambda. This is why the fourth shape reaches only the `[ViewPart]` position: the getter and `ForEach` content positions were never candidates to extend, since neither can host an iterator at all, independent of anything this analysis itself decides. Second, why every worked example threads the loop's own source in as a parameter (`Rows(IReadOnlyList<Item> items)`, §2.7(C)) rather than reading an instance field directly (`foreach (var item in _items)` written inside `Rows`'s own body). This follows from a constraint the iterator shape did not introduce: a `[ViewPart]` method is required to be `static` (`DESIGN.md` §4.3, pre-existing and unrelated to #316), so its body has no `this` and cannot read an instance field at all — not only the loop source, every value a `[ViewPart]` body reads has always had to arrive as a parameter, argument-substituted at each call site the same way any other `[ViewPart]` argument is (§2.7(C)). The iterator shape inherits this existing rule rather than adding a new one. Relaxing `[ViewPart]`'s `static` requirement was raised during this investigation and deliberately not folded into #316: it would affect every `[ViewPart]`, not only the iterator shape, so it is left for its own issue rather than decided as a side effect of this one.

## Appendix C: A Development-Time Fallback (Interpreted Mode)

Only if §2.6's tooling verification finds that a specific environment does not carry a Source Generator re-run through to EnC, room is left to introduce the following DEBUG-build-only fallback.

In a DEBUG configuration, the design-time API family switches by conditional compilation from its inert implementation to a working one (one that builds and wraps a `RenderFragment` inside `View`), and `Body` is evaluated at run time instead of `RenderView`. The whole thing renders inside a single region, using dynamic sequences. Hot Reload then works naturally as a `Body` property body swap (standard EnC support), with no dependence on the SG re-running. In a RELEASE configuration only this specification's generated-code path is used, so shipped performance and size characteristics are unaffected.

This carries the complexity of a doubled render path between development time and run time, so it is not introduced until §2.6's tooling confirmation shows it is necessary.

## Appendix D: Translation Breaks Left Unchecked (Measured Residue)

`DESIGN.md` §4.1 states that what is checked is a translation break, not validity, and places the boundary at whether checking it would commit this repository to authoring and maintaining a table the check depends on — naming, as the unary side's first case, giving a void element children (BCF3016, Appendix A A.1). That standard was revised in #155, but every exclusion in this appendix stays excluded under the revised standard too, because each would still require authoring a table here. This appendix is the list of residue that standard placed outside the check. This is where §4.1 says it has no enumeration, sitting in the same position as `KnownSymbols.CuratedTags` for curated tags and Appendix A A.1 for void elements. What this appendix carries is a break, not invalid output: a shape like `Div.Href("/x")`, which emits exactly what was written and agrees between both render paths, goes unchecked in the same sense but does not belong here (`DESIGN.md` §4.1, #335).

**This is not a work list.** Each item records a position chosen as the result of measurement — it is not a to-do list for widening BCF3016. As with Appendix B, reconsidering an item needs new evidence and a revision of this appendix. "A diagnostic would be kinder" is not evidence.

Every measurement here was taken on 2026-08-03, on net10.0 / ASP.NET Core 10.0.10 / Chromium.

### D.1 The unary side: breaks BCF3016 does not cover

Shapes decidable from the element tag alone, yet not covered by BCF3016. BCF3016 covers exactly one question — can this element take children — and each case below needs a different check and a different fix, so none of them can fold into BCF3016.

**`textarea` / `title` given an element child.** These read their content as text. An element child collapses at page-parse time, and survives when the DOM is built with `appendChild`. `Textarea[Span["x"]]`'s `value` is `"<span>x</span>"` under prerendering and `""` interactively. `Textarea` is a curated helper, so this shape is reachable without going through `Element`.

**Escaped text reaching a raw-text element.** `AddContent` escapes. `script` / `style` / `xmp` / `plaintext` / `noembed` / `noframes` / `noscript` / `iframe` require their content as raw text, so escaping is destructive. `Element("script")["if (a < b) alert(1);"]` emits a body with `<` / `>` / `&` / `'` replaced by unicode escapes, invalid in an operator position, becoming a JS syntax error. `Element("style")` emits HTML entity references, which CSS never decodes. `Element("script")[Raw("…")]` emits correctly, so §4.1's claim that the excluded elements lose no capability still holds — it is the plain spelling that breaks, and it breaks silently. The check here, then, would not say "this element cannot take children" but "this element needs `Raw`" — different prose from BCF3016.

**`textarea` / `pre` dropping a leading newline.** The parser discards one newline immediately following the opening tag; `appendChild` does not. `Pre["\ntext"]` reads as `"text"` under prerendering and `"\ntext"` interactively. Escaping to `&#xA;` does not avoid it, since this rule applies after character-reference decoding. Both are curated helpers. Judging this needs the child string's first character, which is a content check rather than a shape check, and is not always knowable at compile time.

**The four retired, parser-void tags.** `param` / `keygen` / `basefont` / `bgsound` break in exactly the same way as the standard 13 elements, but are deliberately outside BCF3016. §4.1 defines the check's target as the HTML Living Standard's list of void elements precisely so the set tracks the standard rather than being an enumeration nobody could re-derive. These four sit in exclusion group 6 (elements the standard removed), and are reachable only via `Element`.

### D.2 The binary side: breaks that need a (parent, child) relationship

Shapes whose judgment needs the binary relationship (parent, child). This sits outside §4.1's boundary, and is not checked, because it would commit this repository to authoring and maintaining a content-model table here. The binary side mixes two kinds that differ in character, and that mixture itself is one reason the boundary was drawn here.

**A wrong spelling the parser moves around.**

| Output | After the parser reads it |
| --- | --- |
| `<table><div>x</div></table>` | `<div>x</div><table></table>` |
| `<p><div>x</div></p>` | `<p></p><div>x</div><p></p>` (`<p>` goes from one to two) |
| `<table>bare text</table>` | `bare text<table></table>` |

`Div[Col]` diverges without even giving it any children: `col` outside a table is discarded on reparse. `Element("svg")[Element("b")]` escapes the foreign-content subtree. All of these could, in principle, be caught by a diagnostic, but doing so needs the (parent, child) content-model table §4.1 states will not be built.

**A correct spelling the parser normalizes.** `Table[Tr[Td["x"]]]` is the ordinary spelling for writing a table. The parser inserts `tbody`; interactive rendering does not.

- prerender: `table > tbody > tr` matches; `table > tr` does not
- interactive: `table > tr` matches; `table > tbody > tr` does not

A stylesheet written to match either one changes meaning across hydration. There is nothing here a diagnostic could fix, because the code is already correct. If this is worth fixing at all, the place to fix it is the emitting side, or the documentation.

### D.3 Reproduction steps

1. Emit the same `RenderTreeBuilder` frames `RenderView` would emit.
2. Render with `Microsoft.AspNetCore.Components.Web.HtmlRendering.HtmlRenderer` and read `ToHtmlString()`.
3. Assign that string to `innerHTML` in a browser, and compare against a tree built with `appendChild`.

To compare the two render paths against each other, host an Interactive Server app and read the DOM twice: once with `blazor.web.js` blocked, and once after `RendererInfo.IsInteractive` becomes true.

## Appendix E: Values Not Folded (Measured Boundaries)

This lays out the grounds for excluding certain values from §2.7(D)'s static folding. Every one was decided on Chromium, comparing the folded path (`AddMarkupContent`) against the element path (`AddContent` / `setAttribute`). §2.7 defines what gets folded; this records why the boundary sits where it does.

### E.1 The four characters that cannot round-trip through markup

Two of the cases below show that reading the spec alone is not enough — one of them is a character no stage of the spec even touches.

- **Carriage return (CR).** The parser normalizes CRLF and a lone CR to LF during input-stream preprocessing, ahead of tokenization; this holds for fragment parsing of `<template>` too. `setAttribute` / `createTextNode`, on the other hand, do not normalize. An attribute value undergoes no whitespace folding, so the difference shows up directly in `getAttribute` (the folded path returns `"a\nb"` for both `"a\rb"` and `"a\r\nb"`). Of the four, this is the one actually easy to hit — a verbatim string literal in a file fetched with CRLF line endings contains it. LF is not normalized, so it is foldable.
- **NUL.** The shape of the mismatch splits in two by position. The markup path deletes NUL from text content, and replaces it with U+FFFD in an attribute value; the element path preserves it in both. Because the handling sits at tokenization and tree construction rather than preprocessing, the text side and the attribute side never agree.
- **An isolated surrogate.** There is no mismatch; this is a conservative exclusion. By the time .NET encodes the render batch to UTF-8, it is already replaced with U+FFFD, so both paths already carry U+FFFD before it ever reaches the parser. Per spec too, an isolated surrogate in the input stream is a parse error, not a stream rewrite.
- **A leading U+FEFF.** HTML's parse stage never touches this at all. What strips a leading byte-order mark is the browser, when it decodes a render-batch frame string. Because folding is an operation that moves a value's position, when unfolded the value sits at the start of its own frame string and gets stripped, while when folded it sits inside a larger string that starts with `<` and survives. So the exclusion condition here is position, not the character itself. This is the one case where the markup path is actually more faithful to the original — but folding's contract is that both spellings build the same DOM, not which one is closer to the source.

### E.2 Non-string values, and two exceptions

The grounds for excluding a non-string value is the culture in effect at formatting time. Measured: changing `CultureInfo.CurrentCulture` inside a component's `OnInitialized` does not change the attribute output, while changing `CultureInfo.DefaultThreadCurrentCulture` does (#158).

Formatting itself finishes inside the `AddAttribute` call, and what enters the frame is the already-formatted string (measured 2026-08-14, #245). This does not contradict #158's observation: `OnInitialized` and `RenderView` are not guaranteed to run on the same thread, and `CultureInfo.CurrentCulture` is per-thread. The child channel is the same. If a numeric child were allowed, it would resolve to the one overload `AddContent(int, object?)` (every one of `int` / `double` / `decimal` / `DateTime` / an enum resolves here), and this call also calls `ToString` on the spot, stacking the formatted string into the same `Text` frame as passing a `string?` would. A number never even reaches folding, though, since the string stops being constant the moment a number is interpolated — `Span[$"n={3}"]` does not fold, while `Span["n=3"]` does. Together these two mean this item's grounds for exclusion do not distinguish a numeric child from an interpolated string: the grounds for never introducing a numeric-child spelling in the first place lie elsewhere (`DESIGN.md` §4.1, #245). The above are pinned by `NonStringValueFormattingTests` and `ChildValueSpellingTests`.

**Agreement for a constant `null`** was measured in #171. It agrees on the attribute being entirely absent at every level — the element path's frame layer, static SSR, prerendering, the first interactive render, and re-renders in both directions — and is distinguished from `""` at every stage. By contrast, the component parameter path stacks a frame even for `null`, so omission is a property of the element path alone. When the unfolded path writes a constant `null`, though, it carries a `(global::System.String?)` cast: `AddAttribute`'s value position is overloaded, and a bare `null` resolves to neither `string?` nor `MulticastDelegate?`, becoming CS0121 (measured in #234). The element path could match markup exactly by emitting no frame at all too, but a sequence number is assigned against the call that was issued, splitting its treatment from the constant `false` `bool`, which does issue one.

**For a constant `bool`**, that `true` becomes `name=""` was measured as DOM-equivalent. The prerendered output writes the bare `name` with no `=""`, and this too parses to the same DOM. For `false`, the element path emits no frame at all, so the frame count agrees too.

**A bound value is outside this section's scope** (measured 2026-08-14, #307). A `.Bind` that carries a culture wraps the attribute side in `BindConverter.FormatValue(value, culture:)`, so what enters the frame is a string already formatted under the culture written at the call site. Every measurement above comes down to "formatting follows the calling thread's culture," and this path does not follow that. Measured: with the thread holding `de-DE`, a binding that writes `CultureInfo.InvariantCulture` stacks `1234.5` (`NonStringValueFormattingTests`). Whether wrapping happens is decided purely by whether the resolved overload takes a culture, never by the bound value's type, so the existing `string` and `bool` paths' output does not move by a single byte.

This path's cost shows up in trimming, not in formatting (measured 2026-08-14). Binding even one value type keeps the whole of `BindConverter` alive. Comparing a `TrimTestApp` publish with and without a value-type binding: `BindConverter`'s surviving methods rose from 28 to 53, and `Microsoft.AspNetCore.Components.dll` grew from 71,680 to 81,408 bytes (osx-arm64, self-contained, `TrimMode=full`). What survives includes converters for types the app never binds (`ConvertToGuidCore`, for example) — because `FormatterDelegateCache` and `ParserDelegateCache` reference every converter from one place, carrying `[DynamicallyAccessedMembers(All)]` and `UnconditionalSuppressMessage`. This cost is not specific to enum, and never occurs for an app that binds only `string` and `bool`. `TrimmedOutputTests` pins this.

### E.3 Character classes swept out

#150 swept every character class other than E.1's, and measured that all of them agree between the two paths: C0 control characters, DEL, NEL, NBSP, U+2028/U+2029, non-characters in the BMP and the supplementary planes, an internal BOM, U+FFFD itself, tab, LF, runs of whitespace, and a correctly paired surrogate. The only rewrite that occurs during input-stream preprocessing is newline normalization; a surrogate, a non-character, and a control character are merely classified as a parse error and never rewrite the stream.
